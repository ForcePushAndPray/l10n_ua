>
> Це **повністю реалізований рушій із тестами** — усі 6 модулів позначені ✅
> (base — 44 тести, csv — 10, xlsx — 13, xml — 9, api — 12, sftp — 10). Локальний
> файл + CSV-парсер проганяються **без жодних зовнішніх систем** — достатньо файлу з
> диска. Джерела **SFTP** та **HTTP API** потребують доступу до сервера постачальника
> (див. Флоу 2). Деталі архітектури, state machine й моделей —
> у [supplier_prices_architecture.md](../supplier_prices_architecture.md).

> ⚠️ **Примітка:** на цьому демо-сервері модуль може бути **не встановлений**. Тоді

> Локальний файл + CSV проганяються **без зовнішніх систем** — жодних API/SFTP не треба.

Скріншоти — у теці [`img/supplier_prices/`](img/supplier_prices/).

**Де в меню:** рушій вбудовано в застосунок **Закупівлі** → **Supplier Prices**:

| Пункт меню | Призначення |
|-----------|-------------|
| **Imports** | Прогони імпорту (state machine draft → done) |
| **Configuration → Sources** | Джерела прайсів постачальників |
| **Configuration → Mappings** | Маппінг колонок файлу на поля Odoo |

Два незалежні шари налаштовуються на джерелі й комбінуються довільно:

- **fetcher_type** — _звідки_ взяти файл: `manual` (ручне завантаження), `api`, `sftp`;
- **parser_type** — _як_ розібрати файл: `json`, `csv`, `xml`, `xlsx`.

## Флоу 1. Імпорт прайсу з файлу (CSV/XLSX)

> Наскрізний процес «локальний файл прайсу → рядки імпорту → оновлений
> `product.supplierinfo`». Виконується **без жодних зовнішніх систем** — беремо CSV з
> диска, парсимо, застосовуємо. Результат — прогін імпорту в стані **done** і оновлені
> ціни постачальника в картках товарів.

### Крок 1. Створити джерело постачальника

**Закупівлі → Supplier Prices → Configuration → Sources → кнопка `Новий`.**
Відкриється чорнова форма джерела (`l10n_ua.supplier.price.source`). Заповніть:

| Поле | Значення | Коментар |
|------|----------|----------|
| Назва | `Прайс ТОВ «Металбаза»` | довільна |
| Постачальник (`partner_id`) | **ТОВ «Металбаза»** | контрагент, чиї ціни імпортуємо |
| Компанія (`company_id`) | _порожньо_ | порожнє = ціни глобальні для всіх компаній групи |
| Валюта за замовчуванням | UAH | застосовується до рядків без власної валюти |
| Дія на невідомий SKU (`unknown_sku_action`) | **Пропустити (skip)** | варіанти: `skip` / `log_only` / `create_product` / `error_stop` |
| Авто-синхронізація (`auto_sync_active`) | _вимкнено_ | для разового ручного прайсу не потрібна |

**RESULT.** Джерело збережено. Таймаути (`fetch_timeout` 60 с, `parse_timeout` 300 с,
`apply_timeout` 600 с, `watchdog_timeout_minutes` 30) підставляються дефолтними —
захищають воркер від зависання.

> _Скриншот:_ `01-source-form.png` — Форма джерела прайсу

### Крок 2. Обрати parser_type (CSV/XLSX) і fetcher_type (локальний файл)

На тій самій формі джерела задайте два незалежні шари:

| Поле | Значення | Наслідок |
|------|----------|----------|
| **parser_type** | **CSV** | `source_path` у маппінгу = назва колонки (з header) або індекс `2` (без header) |
| **fetcher_type** | **manual** (локальний файл) | файл прикріплюється вручну прямо в імпорт (Крок 4) — нічого налаштовувати не треба |

> Для Excel-прайсу оберіть **parser_type = XLSX** — тоді `source_path` це назва колонки,
> літера `A`/`AC` або індекс; параметри листа (`sheet_name`, `header_row`) задаються в
> `parser_config`. Решта флоу ідентична.

**RESULT.** Джерело знає _як_ розбирати (CSV/XLSX) і _звідки_ брати файл (локально).
Режим `manual` — ідеальний для першого тесту й разових прайсів: жодних зовнішніх
систем.

> _Скриншот:_ `02-parser-fetcher.png` — Вибір parser_type і fetcher_type

### Крок 3. Маппінг колонок

**Configuration → Mappings → `Новий`** (`l10n_ua.supplier.price.mapping`), потім
прив'яжіть маппінг до джерела з Кроку 1.

На рівні маппінгу:

| Поле | Значення | Призначення |
|------|----------|-------------|
| **parser_config** | `{"delimiter": ";", "encoding": "windows-1251", "has_header": true}` | параметри CSV-парсера (типовий український прайс з 1С) |
| **record_path** | _порожньо_ | для табличних форматів (CSV/XLSX) не потрібен |

Приклад вхідного файлу (windows-1251, роздільник `;`, десяткова кома):

```
Артикул;Назва;Ціна;Валюта
А-001;Гайка М8;15,50;UAH
А-002;Болт М10;22,00;UAH
```

Далі — по рядку на кожне цільове поле (`.mapping.field`):

| target | source_path | required | transform | Що робить |
|--------|-------------|:--------:|-----------|-----------|
| **sku** | `Артикул` | ✅ | `strip` | ключ пошуку товару |
| **name** | `Назва` | | `strip` | назва (для нових товарів) |
| **price** | `Ціна` | ✅ | `to_float` | `"15,50"` → `15.50` (обробляє кому) |
| **currency** | `Валюта` | | — | код валюти рядка |

**RESULT.** Мінімально потрібні target — **sku** і **price**. `to_float` знімає
українську кому, `parse_date` з `transform_param = %d.%m.%Y` розбирав би дату
`"17.04.2026"`. Маппінг прив'язано до джерела.

**Повний перелік трансформацій** (`tools/transforms.py`, функція `apply_transform`).
Порожнє/`None` значення повертається без змін (трансформація не застосовується);
`none`/порожній `transform` — значення as-is:

| transform | transform_param | Вхід → вихід | Призначення |
|-----------|-----------------|--------------|-------------|
| `strip` | — | `" А-001 "` → `"А-001"` | прибрати пробіли по краях |
| `upper` | — | `"uah"` → `"UAH"` | верхній регістр |
| `lower` | — | `"UAH"` → `"uah"` | нижній регістр |
| `replace_comma` | — | `"15,50"` → `"15.50"` | кома → крапка (лишається рядком) |
| `to_float` | — | `"15,50"` → `15.5` | у `float`, сам знімає кому й пробіли |
| `to_decimal` | — | `"15,50"` → `Decimal('15.50')` | у `Decimal` (точна арифметика) |
| `parse_date` | `%d.%m.%Y` | `"17.04.2026"` → `date(2026, 4, 17)` | у `date`; готові date/datetime пропускаються як є, дефолтний формат `%Y-%m-%d` |
| `multiply` | `1.15` | `"100"` → `115.0` | помножити на коефіцієнт (див. Флоу 4) — **param обов'язковий** |

Помилка трансформації обов'язкового поля переводить весь прогін у **error** (парсер
кидає `UserError`, `action_parse` ловить і виставляє `state='error'`), причина —
у `error_log`.

> _Скриншот:_ `04-mapping.png` — Маппінг колонок

### Крок 4. Запустити імпорт (state draft → done)

**Supplier Prices → Imports → `Новий`** (або кнопка **Create Import** на джерелі).
Оберіть джерело; оскільки fetcher_type = `manual` — **прикріпіть файл прайсу** з диска.
Далі три кнопки в шапці ведуть імпорт (`l10n_ua.supplier.price.import`) по state
machine:

```
draft → fetching → fetched → parsing → parsed → applying → done
                                                          ↘ error
```

| Кнопка | Метод | Перехід | Що відбувається |
|--------|-------|---------|-----------------|
| **Fetch** | `_do_fetch()` | draft → **fetched** | для `manual` файл уже прикріплено, він потрапляє в `raw_file` |
| **Parse** | `_do_parse()` | fetched → **parsed** | розбирає `raw_file` у рядки `import.line` за маппінгом; raw-файл зберігається — парсинг можна повторити без повторного завантаження |
| **Apply** | `_do_apply()` | parsed → **done** | створює/оновлює `product.supplierinfo` для кожного рядка |

**RESULT введення.** Прогін проходить **draft → done**. Лічильники в шапці:

| Показник | Значення (для прикладу з 2 рядків) |
|----------|-----------------------------------:|
| `line_count` | 2 |
| `matched_count` | 2 |
| `unknown_count` | 0 |
| `error_count` | 0 |

Action-методи **не викидають UserError**: за помилки імпорт переходить у **error**,
причина пишеться в `error_log` і чатер, кнопка **Restart** повертає в `draft`. Рядок у
статусі `unknown` обробляється згідно з `unknown_sku_action` (тут — `skip`).

> _Скриншот:_ `05-import-form.png` — Форма імпорту зі станом done
> _Скриншот:_ `06-import-lines.png` — Рядки імпорту

### Крок 5. Результат — оновлено product.supplierinfo

Після **Apply** для кожного розпізнаного рядка створюється або оновлюється запис
постачальника (`product.supplierinfo`): товар шукається за парою _постачальник +
`product_code` (SKU)_. У картці товару (**Закупівлі → Постачальники**) з'являються:

| Поле supplierinfo | Джерело з прайсу |
|-------------------|------------------|
| Ціна (`price`) | колонка `Ціна` (після `to_float`) |
| Валюта (`currency_id`) | колонка `Валюта` / валюта за замовчуванням джерела |
| Мінімальна кількість (`min_qty`) | target `qty_min` (якщо є в маппінгу) |
| Дата (`date_start`) | target `date_valid` (якщо є) |

Саме ці ціни далі підставляються в замовлення на закупівлю.

> _Скриншот:_ `07-supplierinfo.png` — product.supplierinfo у картці товару

## Флоу 2. Автозавантаження (API/SFTP)

> Той самий пайплайн, але файл **тягнеться з сервера постачальника** автоматично —
> fetcher_type = `api` або `sftp`. Кроки 3–5 (маппінг, запуск, результат) ідентичні
> Флоу 1; відрізняється лише спосіб отримання файлу.
>
> ⚠️ **Потребує доступу до сервера постачальника** (мережа, облікові дані, ключі). Без
> реального ендпоінта цей флоу не проженеш — для локального тесту беріть Флоу 1
> (`manual` + CSV).

### Крок 1. Створити джерело з fetcher_type = api / sftp

Джерело створюється як у Флоу 1 (Крок 1), але **fetcher_type** = **HTTP API** або
**SFTP**. Реквізити підключення задаються JSON-полем **connection_config** на джерелі.

**HTTP API** (`l10n_ua_supplier_prices_api`, потрібен `requests`):

| Ключ connection_config | Приклад | Призначення |
|------------------------|---------|-------------|
| `url` | `https://supplier.example/api/price` | ендпоінт |
| `method` | `GET` | HTTP-метод |
| `auth_type` | `bearer` | `none` / `basic` / `bearer` / `api_key_header` |
| `token` | `***` | облікові дані під обраний auth_type |
| `response_type` | `file` | `file` (тіло = файл) або `json_indirect` (відповідь із посиланням на файл → другий запит за `json_indirect_path`) |

**SFTP** (`l10n_ua_supplier_prices_sftp`, потрібен `paramiko`):

| Ключ connection_config | Приклад | Призначення |
|------------------------|---------|-------------|
| `host` | `sftp.supplier.example` | сервер |
| `port` | `22` | порт |
| `username` | `odoo` | логін |
| `password` / `key_file` | `***` / `/keys/id_rsa` | автентифікація паролем або ключем |
| `remote_path` | `/prices/latest.csv` | шлях до файлу на сервері |
| `host_key_policy` | `reject` | `reject` / `auto_add` / `warning` |

**RESULT.** Джерело знає, з якого зовнішнього ендпоінта тягнути прайс. `parser_type`
(CSV/XML/XLSX/JSON) комбінується довільно — наприклад SFTP + XLSX або API + JSON.

> ⚠️ Наразі облікові дані у `connection_config` зберігаються **відкритим текстом**; для
> production варто винести у `ir.config_parameter` чи зашифроване сховище. Повні схеми
> конфігів усіх завантажувачів — у
> [supplier_prices_architecture.md](../supplier_prices_architecture.md).

> _Скриншот:_ `03-fetcher-type.png` — Вибір fetcher_type = API/SFTP

### Крок 2. Маппінг, запуск і результат

Далі — **як у Флоу 1, Кроки 3–5**:

1. **Маппінг колонок** під обраний parser_type (для XML — `record_path = //product`,
   `source_path` як відносний XPath `./code/text()`, `@sku`; для JSON — `record_path =
   items`, `source_path` dotted `price.value`).

   **XML-парсер** (`_parse_xml`, модуль `l10n_ua_supplier_prices_xml`, залежність `lxml`)
   читає два ключі `parser_config`:

   | Ключ parser_config | Приклад | Призначення |
   |--------------------|---------|-------------|
   | `namespaces` | `{"g": "http://base.google.com/ns/1.0"}` | мапа префіксів NS; використовується і в `record_path`, і в кожному `source_path` (напр. `.//g:price/text()`) |
   | `encoding` | `windows-1251` | примусове перекодування: байти декодуються цим кодуванням і перекодовуються в UTF-8, після чого `_strip_xml_declaration` знімає `<?xml encoding=...?>`, щоб `lxml` не сварився на розбіжність буфера й declaration (1С часто віддає cp1251) |

   Форми `source_path` (відносний XPath від запису): `./code/text()`, `@sku`,
   `./price/@value`, `string(./name)`. Скаляр (рядок/число з `text()`/`@attr`/`string()`)
   або перший вузол списку зводяться до значення; порожнє → `None`.
2. **Запуск імпорту.** Кнопка **Fetch** тепер реально звертається до зовнішнього
   джерела: `_do_fetch()` викликає `_fetch_api()` / `_fetch_sftp()`, тягне файл у
   `raw_file` з `timeout = source.fetch_timeout` → **fetched**. Далі **Parse** → **Apply**
   так само, як у Флоу 1.
3. **Результат** — оновлений `product.supplierinfo` (пошук за партнером + SKU).

**RESULT.** Прогін **draft → done** без ручного прикріплення файлу.

### Крок 3. Авто-синхронізація за розкладом (опційно)

На джерелі увімкніть **auto_sync_active** і задайте **sync_interval_hours** (напр. 24).
Крон `_cron_auto_sync()` шукає активні джерела з `auto_sync_active=True` і створює нові
`draft`-імпорти, коли з `last_sync_date` минув інтервал, після чого проганяє їх
fetch→parse→apply. Constraint `_check_sync_interval` забороняє інтервал < 1 год при
увімкненій авто-синхронізації.

**Чотири рівні захисних таймаутів** на джерелі (`l10n_ua.supplier.price.source`) не
дають імпорту заблокувати воркер:

| Поле джерела | Дефолт | Де перевіряється |
|--------------|-------:|------------------|
| `fetch_timeout` | 60 с | connect+read для API/SFTP (передається в `requests`/`paramiko`) |
| `parse_timeout` | 300 с | deadline-check **на кожному записі** в `_parse_*` (перевищено → `UserError`) |
| `apply_timeout` | 600 с | deadline-check **на кожному чанку** в `_do_apply` |
| `watchdog_timeout_minutes` | 30 хв | крон-сторож переводить застряглі прогони в `error` |

**Батчі й commit у `_do_apply`.** Apply обробляє рядки чанками по **500** з
`self.env.cr.commit()` після кожного чанку. Це: (1) звільняє row-locks на
`product.supplierinfo`, аби інші процеси не чекали; (2) оновлює `write_date`, тож
watchdog бачить активність і не зарахує прогін як застряглий; (3) обмежує пам'ять на
прайсах 50k+ рядків. Через find-or-create по парі _партнер + `product_code`_ повторний
`action_apply` після обриву безпечний — уже закомічені рядки просто перезапишуться.

**Watchdog** (`_cron_watchdog()`, крон кожні 5 хв) бере прогони в станах
`fetching/parsing/applying` і, якщо `write_date` старіший за `watchdog_timeout_minutes`
джерела, переводить їх у `error` через `_set_state` — зависла мережа чи вбитий воркер
не лишать імпорт «висіти» назавжди.

**RESULT.** Прайс постачальника оновлюється автоматично, без участі оператора; будь-який
збій обмежений таймаутами й перехоплений сторожем.

## Флоу 3. Обробка невідомих (нових) SKU

> Що робити, коли позиції прайсу немає в номенклатурі. Поведінка керується **одним
> полем джерела** `unknown_sku_action` і виконується на кроці **Apply** методом
> `import.line._handle_unknown_sku()`.

### Крок 1. Як шукається товар

`import.line._find_product()` шукає `product.product` **виключно** за парою
_постачальник + `product_code`_ у `product.supplierinfo`:

```
domain = [('partner_id', '=', partner.id), ('product_code', '=', supplier_sku)]
```

⚠️ Зіставлення — **тільки за артикулом (SKU)**. Поля `barcode` і `supplier_name` на
рядку заповнюються з прайсу й зберігаються, але **в пошуку не беруть участі**;
зіставлення за штрихкодом, за назвою та порогу схожості (fuzzy) **немає**. Прайси без
стабільних артикулів даватимуть багато `unknown`.

### Крок 2. Обрати політику `unknown_sku_action` на джерелі

| Значення | Метод-гілка | Статус рядка | Наслідок |
|----------|-------------|--------------|----------|
| **skip** (дефолт) | `self.status = 'skipped'` | `skipped` | рядок пропущено, `supplierinfo` не чіпається — безпечний дефолт |
| **log_only** | `self.status = 'unknown'` | `unknown` | лишити для ручного розбору контент-менеджером; `supplierinfo` не створюється |
| **error_stop** | `raise ValidationError` | `error` | виняток спливає до `action_apply` → **весь прогін** у `error` |
| **create_product** | `create('product.product')` | `created` | створити товар і **продовжити** до створення `supplierinfo` |

### Крок 3. Що створює `create_product`

Для `create_product` створюється `product.product` з полями:

| Поле product.product | Значення з рядка |
|----------------------|------------------|
| `name` | `supplier_name` (або `supplier_sku`, якщо назви немає) |
| `default_code` | `supplier_sku` |
| `barcode` | `barcode` рядка (або `False`) |
| `type` | `'consu'` (складський/витратний) |
| `purchase_ok` | `True` |

**RESULT.** На відміну від `skip`/`log_only`/`error_stop`, гілка `create_product` **не
перериває** `_apply_to_supplierinfo` — одразу після створення товару рядок іде далі й
отримує запис `product.supplierinfo` з ціною. Лічильник шапки `matched_count` рахує
рядки в статусах `matched` **і** `created`; `unknown_count` — тільки `unknown`. Кожен
`import.line` зберігає власний `status` і `error_message` для аудиту (видно, чому рядок
пропущено чи який товар створено).

> Порада: `skip`/`log_only` — для перших тестів і прайсів із розбіжними кодами;
> `create_product` — лише для довірених повних прайсів, інакше засмітите номенклатуру.

> _Скриншот:_ `08-unknown-sku.png` — Політика unknown_sku_action на джерелі
> _Скриншот:_ `09-created-product.png` — Товар, створений із рядка прайсу

## Флоу 4. Переоцінка / націнка (обмежено)

> ⚠️ **Аудит-примітка про повноту.** Повноцінного **рушія правил націнки/переоцінки**
> в домені **НЕМАЄ**. `price` записується в `product.supplierinfo` **як є**, у валюті
> рядка або `currency_default_id` джерела. Немає умовних правил по групах товарів,
> брендах, обсягах чи курсі валют на дату прайсу; немає історії курсів НБУ на
> `date_valid`. Фінальна **продажна** націнка лишається за межами домену — це стандартний
> прайсинг Odoo поверх закупівельної ціни.

### Єдиний важіль коригування ціни — transform `multiply`

Єдиний спосіб змінити число прайсу — column-level трансформація `multiply` на полі
маппінгу `price` (див. Флоу 1, Крок 3). Вона множить значення на **фіксований
коефіцієнт** із `transform_param` під час парсингу:

| Поле маппінгу (`.mapping.field`) | Значення |
|----------------------------------|----------|
| target | `price` |
| source_path | `Ціна` |
| transform | **`multiply`** |
| transform_param | `1.15` (обов'язковий; без нього — `TransformError`) |

Приклад: `"100"` у прайсі → `115.0` у `supplierinfo`. Коефіцієнт застосовується
**однаково до всіх рядків** — це технічна поправка (напр. груповий курсовий множник),
а **не** бізнес-правило націнки з умовами.

**RESULT.** Хочете диференційовану переоцінку по групах/брендах/обсягах — її треба
робити поза цим доменом (стандартні прайс-листи продажів Odoo, або окремий рушій).
Тут доступний лише один плаский множник на колонку.
