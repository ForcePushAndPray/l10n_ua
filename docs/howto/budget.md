# HOWTO: Бюджетні установи (держсектор) — робочі флоу

← [Назад до документації](../../README.md) · [Опис домену](../budget.md)

> Покрокові **робочі процеси** обліку бюджетної установи: план рахунків держсектору,
> бюджетні класифікатори, кошторис із контролем виконання, обмін із ДКСУ та регламентна
> звітність. Стек **реалізований і покритий тестами** (`test_budget_estimate.py`,
> `test_budget_limit.py`, `test_classifications.py`, `test_dbf_reader.py`, `test_reports.py`).
>
> **Важливо — про це демо.** [demo.ndev.online](https://demo.ndev.online) (компанія
> _ТОВ «Тестова Компанія»_, вхід `demo`/`demo`) — це **комерційна** організація на
> звичайному Плані рахунків. Модуль бюджету на ній **НЕ встановлено**, тож флоу нижче
> проходяться на **окремій держсекторній базі** (`-i l10n_ua_budget`), а числа взято з
> тестів і фікстур, а не з живих документів демо. Дані на робочій базі не видаляються —
> її можна наповнювати під час тестування.
>
> **Обмін із Державною казначейською службою** (реальні виписки, формати файлів, маппінг
> полів DBF) потребує **клієнт-специфічного налаштування** під конкретну версію ПЗ
> Казначейства — це свідомі точки розширення (див. Флоу 3). Решта флоу (класифікатори,
> кошторис, контроль ліміту, звітність) проходиться повністю.

Скріншоти — плейсхолдери у теці [`img/budget/`](img/budget/) (імена файлів вказані біля кроків).

## Флоу 1. Первинне налаштування держсекторної бази

> Одноразове розгортання: окремий план рахунків №1203 + довідники бюджетної класифікації.
> Результат — заповнені довідники, з якими вже можна складати кошторис.

### Крок 0. Встановити стек бюджетника

Увесь стек ставиться одним модулем-збіркою `l10n_ua_budget` (`application: True`), який
тягне `base`, `chart_template`, `estimate`, `treasury`, `reports`:

```bash
# Увесь стек одним модулем-збіркою:
./venv311/bin/odoo -d odoo19budget -i l10n_ua_budget --stop-after-init

# Або окремі модулі:
./venv311/bin/odoo -d odoo19budget -i l10n_ua_budget_base,l10n_ua_budget_estimate --stop-after-init
```

Після входу в меню застосунків (сітка ▤) з'являються розділи домену:

| Розділ | Призначення |
|--------|-------------|
| **Бюджетні класифікатори** | КЕКВ, КФК, КПКВК, КВКВ (ГРБК), фонди |
| **Кошториси** | Розпис за КЕКВ, план vs факт, контроль виконання |
| **Казначейство (ДКСУ)** | Органи ДКСУ, казначейські журнали, імпорт виписок |
| **Бюджетна звітність** | Кошторис, форми 2д/2м/4-1д/4-2д/7д/9д, меморіальні ордери |

> _Скриншот:_ `00-apps-menu.png` — Меню застосунків домену бюджету

### Крок 1. Встановити план рахунків держсектору (Наказ Мінфіну № 1203)

**Бухгалтерія → Конфігурація → Пакет локалізації → обрати шаблон `ua_state`.**
Держсекторний облік ведеться на **окремому плані рахунків** — Наказ Мінфіну № 1203 від
31.12.2013 (модуль `l10n_ua_budget_chart_template`, `code_digits='4'`), що завантажується
через API `account.chart.template` Odoo 19.

Що робить шаблон (результат встановлення):

| Параметр | Значення |
|----------|----------|
| Код шаблону | `ua_state` |
| Розрядність коду | 4 знаки |
| К-ть субрахунків | ~95 по класах держсектору |
| Класи | 1 (необоротні 10–15), 2 (фін. активи, запаси 18–25), 5 (капітал, фонди 51–55), 6 (зобов'язання 60–67), 7 (доходи 70–75), 8 (витрати 80–85), 0 (позабалансові) |
| Прапорець на рахунках | `ua_budget_is_state_sector=True` |
| Властивості за замовч. | дебіторка `2117`, кредиторка `6614`, витрати `8013`, доходи `7411` |
| Журнали | реєстраційний рахунок ДКСУ, каса, закупівлі, доходи від платних послуг |

> ⚠️ План **не звірявся** з останньою редакцією (Наказ № 1219 від 30.12.2022). Перед
> продуктивом звірте на zakon.rada.gov.ua/laws/show/z0161-14.

> _Скриншот:_ `01-chart-1203.png` — План рахунків держсектору №1203

### Крок 2. Імпорт класифікаторів КПКВК / КЕКВ / КФК / КВКВ

Довідники бюджетної класифікації дає `l10n_ua_budget_base`. Частина сідиться одразу при
встановленні, КПКВК — оновлюється щороку через wizard.

**2.1. Сідові довідники (наповнюються автоматично з CSV при встановленні):**

| Класифікатор | Модель | К-ть | Особливості | Підстава |
|--------------|--------|-----:|-------------|----------|
| **КЕКВ** (економічна) | `l10n_ua.kekv` | ~58 | ієрархія `_parent_store`, 2/3/4-знач. коди, тип видатків, `full_name` | Наказ Мінфіну № 333 |
| **КФК** (функціональна) | `l10n_ua.kfk` | ~84 | ієрархія, 4-знач., обчислюваний `division` (перші 2 цифри) | Наказ Мінфіну № 11 |
| **КВКВ** (відомча, ГРБК) | `l10n_ua.kvkv` | ~15 | 3-знач. код головного розпорядника | — |
| **КПКВК** (програмна) | `l10n_ua.kpkvk` | 4 (мінімум) | 7-знач. код (3 КВКВ + 4 програма), автоприв'язка `kvkv_id`, ключ код+рік | Наказ Мінфіну № 11 |

**2.2. Масовий імпорт КПКВК через wizard** (`l10n_ua.kpkvk.import`, модуль
`l10n_ua_budget_kpkvk_import`) — оскільки довідник оновлюється щороку.

**Бюджетні класифікатори → КПКВК → Імпорт.** Заповнити:

| Поле | Значення |
|------|----------|
| Файл | CSV (`code,name[,description]`) або DBF (синоніми KOD/NAZVA) |
| Кодування | налаштовується (для DBF типово CP866) |
| Рік | напр. 2026 |
| Режим overwrite | оновити наявні записи код+рік |

**RESULT.** Upsert по ключу код+рік; після імпорту wizard показує протокол:
**створено / оновлено / пропущено**. Звірено тестом `test_kpkvk_import.py`.

> **Результат Флоу 1:** довідники КЕКВ (~58), КФК (~84), КВКВ (~15) заповнені сідом;
> КПКВК наповнено з файлу за рік; план рахунків №1203 активний. Можна складати кошторис.

> _Скриншот:_ `02-classifiers.png` — Довідники бюджетної класифікації
> _Скриншот:_ `03-kpkvk-import.png` — Wizard імпорту КПКВК: протокол

## Флоу 2. Кошторис із контролем виконання

> Центральний документ установи: помісячний розпис за КЕКВ у розрізі фонду, машина станів
> і контроль касового виконання (асигнування vs факт). Модель `l10n_ua.budget.estimate`
> (`l10n_ua_budget_estimate`), поведінка звірена `test_budget_estimate.py` (162 рядки).

### Крок 1. Створити кошторис (шапка + рядки за КЕКВ)

**Кошториси → Новий.** Заповнити шапку:

| Поле | Значення (приклад) |
|------|--------------------|
| Рік | 2026 |
| Фонд | Загальний / Спеціальний / Обидва |
| КПКВК | 1011010 _(звідси похідні КФК і КВКВ)_ |
| Дати періоду | 01.01.2026 – 31.12.2026 |
| Номер | **підставляється автоматично** через `ir.sequence`, унікальність номер + установа + рік |

На вкладці **Рядки розпису** додати рядки — кожен рядок (`l10n_ua.budget.estimate.line`)
це КЕКВ у розрізі фонду з **помісячним розписом** `m01…m12`:

| Поле | Значення (приклад) |
|------|--------------------|
| КЕКВ | 2111 «Заробітна плата» |
| Фонд | Загальний |
| m01…m12 | напр. по 100 000,00 ₴ на місяць |

**RESULT (обчислюється одразу).** Із помісячного розпису система рахує:

| Показник | Значення |
|----------|---------:|
| Квартали `q1–q4` | 300 000,00 ₴ кожен |
| **Річний план** | **1 200 000,00 ₴** |
| Касове виконання `amount_actual` | 0,00 ₴ _(поки немає проведених проводок)_ |
| Залишок | 1 200 000,00 ₴ |
| % виконання | 0 % |

> Constrains не пускають **від'ємні** суми та рядок, чий фонд **суперечить** фонду шапки.

> _Скриншот:_ `04-estimate-form.png` — Форма кошторису: шапка
> _Скриншот:_ `05-estimate-lines.png` — Рядки розпису КЕКВ × фонд × місяці

### Крок 2. Затвердити кошторис (машина станів)

У шапці — статусний ланцюжок (`mail.thread`, історія в чатері), кнопки-переходи з валідацією:

**Чернетка → Подано → Затверджено → Виконується → Закрито** (+ Скасовано, повернення в чернетку).

Натиснути **`Подати`**, далі **`Затвердити`** (заповнюються дата й автор затвердження).

**RESULT.** Кошторис у стані **Затверджено**. Тільки з цього моменту він бере участь у
контролі ліміту (Крок 3). Зміни до затвердженого кошторису оформлюються як версії-довідки
(`is_amendment`, `parent_estimate_id`), а не редагуванням оригіналу.

### Крок 3. Контроль виконання: асигнування vs факт

Касове виконання рахується автоматично: поле `amount_actual` кожного рядка агрегується з
**проведених** `account.move.line` за ключем **рік / КЕКВ / фонд / КПКВК** (`read_group`
по дебету). Далі — залишок і % виконання.

**RESULT — жива картина план vs факт** (приклад по рядку 2111 після проведення видатків
на 250 000 ₴):

| Показник | Значення |
|----------|---------:|
| Річний план (асигнування) | 1 200 000,00 ₴ |
| Касове виконання (факт) | 250 000,00 ₴ |
| **Залишок** | **950 000,00 ₴** |
| % виконання | 20,8 % |

**Попередження / блокування при перевищенні ліміту.** `l10n_ua.budget.limit.checker`
вмикається при проведенні (`account.move._post`) документів **казначейських** журналів:

1. сумує **дебет** за (рік, КЕКВ, фонд, КПКВК);
2. знаходить рядки **затверджених** кошторисів за тим самим ключем;
3. кидає **`UserError`**, якщо ліміту немає взагалі **або** дебет перевищує залишок
   (план − факт).

Підстава — Бюджетний кодекс ст. 48, ПКМУ № 938. Три сценарії (дозвіл у межах ліміту,
блок при перевищенні, блок за відсутності кошторису) звірені `test_budget_limit.py`
(206 рядків).

> **Результат Флоу 2:** кошторис затверджено; факт підтягується з проводок автоматично;
> спроба провести видаток понад залишок блокується з поясненням.

> _Скриншот:_ `06-treasury-limit.png` — Контроль ліміту асигнувань: UserError при перевищенні

## Флоу 3. ДКСУ (Казначейство) + DBF

> Обмін із Державною казначейською службою. **Клієнт-специфічна точка розширення:**
> базовий механізм є й покритий тестами, але реальний формат виписки конкретного органу
> ДКСУ треба звірити з семплом. Модулі `l10n_ua_budget_treasury` (+ плагін `_dbf`).

### Крок 1. Органи ДКСУ та казначейські журнали

- **`l10n_ua.treasury.organ`** — довідник територіальних органів ДКСУ (центральний апарат,
  обласні ГУДКСУ, районні УДКСУ; ієрархія, область, ЄДРПОУ), сід **~28 записів**;
- на **`account.journal`** з'являються: прапорець казначейського рахунку, тип
  (реєстраційний / спеціальний / депозитний / поточний), орган ДКСУ, КПКВК, фонд і
  вимикач перевірки ліміту (він і вмикає контроль із Флоу 2, Крок 3).

### Крок 2. Імпорт виписки ДКСУ

**Казначейство (ДКСУ) → Імпорт виписки** — wizard `l10n_ua.treasury.statement.import`.

- **Базовий режим (skeleton):** розбирає простий **CSV**
  (`date,description,partner_name,amount,reference`) → створює `account.bank.statement`;
- реальні формати підключаються через метод-розширення **`_parse_custom()`**.

### Крок 3. Виписки у форматі DBase (DBF) — маппінг полів

Найпоширеніший експорт АС Казначейства — **DBase III/IV**, його дає плагін
`l10n_ua_budget_treasury_dbf`:

- `dbf_reader.py` — чистий Python-парсер DBF **без зовнішніх залежностей** (заголовок,
  дескриптори полів, записи; типи C/N/F/D/L; пропуск memo й видалених; кодування CP866
  з fallback); звірено `test_dbf_reader.py` (134 рядки);
- override `_parse_custom()` мапить поля виписки через **`_dbf_field_map()`** (синоніми
  DOC_NUM / DOC_DATE / SUM / NAZ_PRIZ / KOD_KOR / NAZ_KOR / DT_KT) і визначає знак суми за
  напрямом дебет/кредит.

> ⚠️ **Точки розширення під клієнта:** назви полів різняться між версіями ПЗ Казначейства —
> `_dbf_field_map()` **треба звірити з реальним семплом** і за потреби переозначити у
> дочірньому (клієнтському) модулі. Так само `_parse_custom()` для нестандартного CSV/іншого
> формату. На цьому демо реальний обмін не проходиться (немає під'єднаного органу ДКСУ).

> _Скриншот:_ `07-statement-import.png` — Wizard імпорту виписки ДКСУ

## Флоу 4. Бюджетна звітність

> Друковані форми й регламентна звітність розпорядників — `l10n_ua_budget_reports`.
> Рендер звірено `test_reports.py` (80 рядків). **Бюджетна звітність → …**

- **Кошторис** — QWeb-друк за Наказом № 44 (кнопка **Друк** у самому кошторисі);
- **Форма 2д** «Звіт про надходження та використання коштів загального фонду» — wizard
  `budget_form_2d.wizard`: вибір періоду (квартал / півріччя / 9 міс. / рік), розрахунок
  **план vs факт** по КЕКВ загального фонду з `account.move.line`;
- **Мультиформ** (`budget.multi_form.wizard`):

  | Форма | Зміст |
  |-------|-------|
  | **2м, 4-1д, 4-2д** | Виконання по фонду |
  | **7д** | Кредиторська заборгованість (`liability_payable`) |
  | **9д** | Дебіторська заборгованість (`asset_receivable`) |

- **Меморіальні ордери МО-1…МО-17** (`memorial_order.wizard`): для кожного МО задано набір
  типів рахунків / кодів / префіксів / фонду; вибірка проводок за період із підсумками
  дебету та кредиту.

> Маппінги меморіальних ордерів на рахунки — **евристичні** (за типовою кореспонденцією);
> під облікову політику конкретної установи можуть потребувати уточнення.
