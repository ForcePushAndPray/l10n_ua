## Передумови (зовнішнє підключення)

> **Важливо — що можна пройти наживо на демо, а що ні.**
>
> | Флоу | Потрібні зовнішні ключі? | Наживо на демо |
> |------|--------------------------|----------------|
> | **Флоу 1. Курси валют НБУ** | ❌ Ні (публічний ендпоінт `bank.gov.ua`) | ✅ Проходиться повністю |
> | **Флоу 2. ПриватБанк** | ✅ Токен Автоклієнта або merchant-дані | ⛔ Тільки налаштування; завантаження виписки — ні |
> | **Флоу 3. monobank** | ✅ Персональний токен `api.monobank.ua` | ⛔ Тільки налаштування; завантаження виписки — ні |
> | **Флоу 4. QR-посилання** | QR НБУ — ❌ ні; еквайринг mono — ✅ токен мерчанта | ✅ QR НБУ так; оплата mono — ні |
>
> Банківські інтеграції ПриватБанк і monobank звертаються до **реальних API банків** з вашим
> токеном. Цих ключів **немає на демо-сервері**, тому реальне завантаження виписок наживо на демо
> **не виконується** — відповідні кроки нижче описують налаштування, а живий запуск потребує
> ваших власних облікових даних. **Синхронізація курсів НБУ винятків не має — вона працює без
> жодних ключів.**
>
> Що потрібно отримати заздалегідь:
>
> - **ПриватБанк (Автоклієнт):** у кабінеті **Privat24 for Business → «Автоклієнт»** увімкнути
>   доступ, згенерувати **токен** і скопіювати **IBAN рахунку**. Для старих інтеграцій — merchant id
>   + пароль + номер картки (legacy Merchant API).
> - **monobank:** персональний **токен** на [api.monobank.ua](https://api.monobank.ua) (кнопка
>   «Отримати токен» через застосунок). Токен дає доступ до `personal/statement`.
> - **Еквайринг monobank** (для платіжних посилань): окремий токен мерчанта monobank Acquiring,
>   що вписується у поле банківського журналу.

## Флоу 1. Синхронізація курсів валют НБУ

> Наскрізний процес «джерело курсів → синхронізація → курси у `res.currency.rate`».
> **Працює без будь-яких ключів** і повністю відтворюється наживо на демо
> (модуль `l10n_ua_bank_currency_sync`, модель `res.currency.rate.provider`).

### Крок 1. Активувати валюти

**Бухгалтерія → Конфігурація → Валюти** (або меню валют). Увімкніть валюти, курси яких треба
тягнути (USD, EUR тощо) — прапорцем **Активна**. Неактивні валюти в синхронізацію не потрапляють.

> Компанія демо працює у **UAH**. Для не-гривневих компаній модуль коректно перераховує
> крос-курс (`_uah_per_company_unit`, `_rate_vals`), тож курс завжди зберігається відносно
> валюти компанії.

### Крок 2. Створити провайдера курсів

**Банк UA → Курси валют → `Новий`** (модель `res.currency.rate.provider`). Заповніть:

| Поле | Значення |
|------|----------|
| Назва (`name`) | Курси НБУ |
| Провайдер (`code`) | **НБУ** (`nbu`) |
| Валюти для синхронізації (`currency_ids`) | _порожньо_ = всі активні (або оберіть USD, EUR) |
| Авто-синхронізація (`auto_sync`) | ☐ (увімкнути для планового крону) |

> Альтернативні джерела того ж поля `code`: **ПриватБанк** (`privatbank`, з вибором типу курсу
> `privat_rate_type`: готівковий `5` / безготівковий `11`) та **monobank** (`monobank`). Обмеження
> — один провайдер кожного типу на компанію (`_unique_code_company`).

> _Скриншот:_ `07-currency-provider.png`

### Крок 3. Запустити синхронізацію (результат введення)

Натисніть **`Синхронізувати`** (`action_sync_rates()`, або майстер синхронізації). Система звертається
до ендпоінта НБУ
`https://bank.gov.ua/NBUStatService/v1/statdirectory/exchange?json&date=YYYYMMDD`
і записує курси. Очікуваний **результат**:

| Показник | Результат |
|----------|-----------|
| Записи у `res.currency.rate` | створено/оновлено на дату синхронізації |
| Поле **Остання синхронізація** (`last_sync_date`) | оновлено поточним часом |
| Курс USD/EUR у картці валюти | відповідає офіційному курсу НБУ на дату |
| Історія курсів | зберігається (по одному запису на дату) |

Для планового оновлення увімкніть **cron** синхронізації (або `auto_sync` на провайдері).

> Модуль покрито тестами `tests/test_cross_rate.py` (8 сценаріїв: реципрокність гривні,
> крос-курс для не-UAH компанії, ігнорування «сирих» котирувань, крос-курс monobank тощо).

> _Скриншот:_ `08-currency-rates.png`

## Флоу 2. ПриватБанк (Автоклієнт / API)

> Імпорт банківської виписки ПриватБанку в проводки (модуль `l10n_ua_bank_privat`, провайдер
> `privat`). **Наживо на демо не проходиться повністю** — крок 2 (завантаження) потребує реального
> токена Автоклієнта. Кроки 1 і 3 описують налаштування та очікуваний результат.

### Крок 1. Ввести облікові дані у конфігурації синхронізації

**Банк UA → Конфігурації синхронізації → `Новий`** (модель `l10n_ua.bank.sync.config`).
Одна конфігурація = один банківський рахунок. Заповніть:

| Поле | Значення |
|------|----------|
| Провайдер (`provider`) | **PrivatBank** (`privat`) |
| Банківський журнал (`journal_id`) | банківський журнал ПриватБанку (тип `bank`) |
| **API Token** (`privat_api_token`) | токен з Privat24 Business → Автоклієнт |
| **Account IBAN** (`privat_account_iban`) | UA + 27 цифр |
| _(legacy)_ Merchant ID / Password / Card (`privat_merchant_*`) | лише для старого Merchant API |

> Гілка отримання виписок обирається **за наявними даними**: якщо є `privat_api_token` — сучасний
> **Автоклієнт**; якщо лише merchant-дані — legacy. Банківський журнал прив'язується до конфігу;
> `res.bank` зберігає код **МФО**, `res.partner.bank` валідує **IBAN**.

Натисніть **`Перевірити підключення`** (`action_test_connection()`) — звернення до API з токеном.

> **Наживо на демо не виконується** — потрібен реальний токен Автоклієнта.

> _Скриншот:_ `05-privat-config.png`

### Крок 2. Завантажити виписку (потрібен токен)

**Банк UA → Завдання синхронізації** (модель `l10n_ua.bank.sync.job`, машина станів
`draft → fetching → fetched → processing → done` / `error`):

1. Створіть завдання від конфігурації, вкажіть **період** (`date_from` / `date_to`).
2. **`Завантажити`** — `_fetch_from_bank()` → `_privat_fetch_autoclient()`:
   `GET https://acp.privatbank.ua/api/statements/transactions` із заголовком **`token`** і
   параметрами `startDate` / `endDate` / `acc`. Сирий payload зберігається (`payload_fetched_at`).
   _(Legacy-гілка `_privat_fetch_merchant()` → `https://api.privatbank.ua/p24api/rest_fiz`,
   XML-запит `cmt`.)_
3. **`Обробити`** (`action_process`) — `_parse_transactions()` розбирає payload у виписку
   (`l10n_ua.bank.statement`) й окремі транзакції (`l10n_ua.bank.transaction`).

> Сирий payload зберігається — повторну обробку можна запустити **без повторного завантаження**
> з банку (зручно при відлагодженні правил).

> **Наживо на демо не виконується** — крок вимагає реального токена.

> _Скриншот:_ `02-sync-job.png`, `03-transactions.png`

### Крок 3. Результат: транзакції імпортовано, рознесення по рахунках

Очікуваний **результат** після обробки:

| Показник | Результат |
|----------|-----------|
| Виписка (`l10n_ua.bank.statement`) | створена за період, з підсумками |
| Транзакції (`l10n_ua.bank.transaction`) | по одній на операцію; поля контрагента (назва, IBAN, ЄДРПОУ) |
| Прапорець `is_reconciled` / `matched_rule_id` | проставлені, якщо спрацювало правило співставлення |
| Кнопка **`Створити проводку`** (`action_create_move()`) | формує `account.move` |

**Рознесення по рахунках.** Рахунок-кореспондент бере **правило співставлення** (крок 3.1),
інакше — транзитний рахунок. Додатково: експорт виписки у **XLSX**
(`/l10n_ua_bank_sync/export_statement_xlsx/<id>`) і QWeb-звіт виписки.

#### Крок 3.1. Правила авто-співставлення

**Банк UA → Правила співставлення** (`l10n_ua.bank.match.rule`). Правило (`check_match`)
співставляє транзакцію з **рахунком-кореспондентом** (`account_id`), **контрагентом** і **міткою**
та автоматично проставляє їх під час обробки завдання — так проводки створюються без ручного
вибору рахунку.

> _Скриншот:_ `04-match-rules.png`

## Флоу 3. monobank (токен)

> Імпорт виписки monobank через **Personal Statement API** (модуль `l10n_ua_bank_mono`, провайдер
> `mono`). Логіка ідентична Флоу 2, відрізняється джерелом і токеном. **Наживо на демо не
> проходиться** — потрібен персональний токен monobank.

### Крок 1. Ввести токен у картці конфігурації

**Банк UA → Конфігурації синхронізації → `Новий`**. Заповніть:

| Поле | Значення |
|------|----------|
| Провайдер (`provider`) | **monobank** (`mono`) |
| Банківський журнал (`journal_id`) | банківський журнал monobank |
| **API Token** (`mono_api_token`) | персональний токен (заголовок `X-Token`) |
| **Account ID** (`mono_account_id`) | ID рахунку _(або залишити для автовизначення гривневого)_ |

Натисніть **`Отримати рахунки`** (`action_fetch_accounts()`) — підтягне список рахунків із
балансами через `/personal/client-info`; **`Перевірити підключення`** (`action_test_connection()`)
валідує токен. `_mono_get_default_account()` автоматично визначає гривневий рахунок (валюта **980**).

> **Webhook:** поле `mono_webhook_url` обчислюється (`/l10n_ua_bank_mono/webhook/<id>`) і є прапорець
> `mono_webhook_active`, але **контролер webhook у модулі не реалізований** — real-time оновлення
> поки заглушка. Синхронізація працює через опитування (fetch job).

> **Наживо на демо не виконується** — потрібен реальний персональний токен monobank.

> _Скриншот:_ `06-mono-config.png`

### Крок 2. Завантажити виписку (потрібен токен)

Завдання синхронізації (як у Флоу 2, крок 2):

1. Створіть завдання, вкажіть **період** (обмеження API monobank — **31 день**).
2. **`Завантажити`** — `_fetch_from_bank()`:
   `GET https://api.monobank.ua/personal/statement/{account}/{from}/{to}` із заголовком **`X-Token`**;
   обробляється `429` (rate limit).
3. **`Обробити`** — `_parse_transactions()` переводить суми з **копійок у гривні**, знак задає напрям
   (Дт/Кт), витягує назву / IBAN / ЄДРПОУ контрагента.

> **Наживо на демо не виконується.**

### Крок 3. Результат: транзакції імпортовано, рознесення по рахунках

Результат такий самий, як у Флоу 2, крок 3:

| Показник | Результат |
|----------|-----------|
| Виписка + транзакції | створені за період; суми у гривнях, напрям за знаком |
| Контрагент | назва / IBAN / ЄДРПОУ витягнуті з payload |
| Правила співставлення | проставляють рахунок-кореспондент і контрагента |
| **`Створити проводку`** | `account.move`; рахунок — з правила, інакше транзитний |

> _Скриншот:_ `03-transactions.png`

## Флоу 4. Платіжне QR-посилання

> Формування платіжних посилань для рахунків (`account.move`) і замовлень (`sale.order`)
> (модуль `l10n_ua_payment_link`). **QR НБУ працює без ключів і проходиться наживо**; посилання-оплата
> monobank потребує токена еквайрингу.

### Крок 4a. QR НБУ (без ключів — наживо працює)

**Бухгалтерія → Документи → відкрити рахунок.** Поле `nbu_payment_link` формується автоматично за
шаблоном (`ir.config_parameter l10n_ua.nbu_qr_template`, **Постанова НБУ №11 від 01.02.2021**),
кодується `base64url`, посилання — `https://bank.gov.ua/qr/<payload>`.

| Крок | Дія / результат |
|------|-----------------|
| Реквізити | беруться з рахунку/компанії (зовнішнє підключення не потрібне) |
| QR-код | рендериться у SVG data-URI (бібліотека `qrcode`) |
| Друк | **друкована форма рахунку з QR** (`report_invoice_inherit`) містить QR для сплати з банку |

> **Результат:** клієнт сканує QR у застосунку свого банку — реквізити й сума підставляються
> автоматично. Проходиться наживо на демо повністю.

> _Скриншот:_ `09-nbu-qr.png`

### Крок 4b. Еквайринг monobank (потрібен токен мерчанта)

1. У **банківському журналі** (`account.journal`) вкажіть **токен еквайрингу monobank**
   (`mono_acquiring_token`; також доступно через `res.config.settings`).
2. На рахунку/замовленні натисніть **`Створити посилання mono`** (`action_create_mono_link()`):
   `POST https://api.monobank.ua/api/merchant/invoice/create` із токеном журналу; передаються
   позиції рахунку та `webHookUrl`.
3. **Результат:** зберігаються `mono_payment_link` (pageUrl для оплати) і `mono_invoice_id`.

Підтвердження оплати — контролер `/l10n_ua_payment_link/mono/webhook`: за `invoiceId` і
`status == 'success'` знаходить замовлення/рахунок і **проводить оплату**.

> **Наживо на демо не виконується** — потрібен реальний токен мерчанта monobank Acquiring.

> _Скриншот:_ `10-mono-acquiring.png`
