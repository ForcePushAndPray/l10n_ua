## Передумови (зовнішнє підключення)

> **ВАЖЛИВО — фіскалізацію наживо на демо виконати НЕ можна.** Модулі
> `l10n_ua_prro_base` та `l10n_ua_prro_checkbox` реалізують клієнт до API Checkbox
> (`https://api.checkbox.in.ua/api/v1/`), але **самі по собі нічого не
> фіскалізують**. Щоб реально відкрити зміну, зареєструвати чек чи сформувати
> Z-звіт, потрібні:
>
> - **діючий акаунт Checkbox** (юрособа/ФОП, договір із сервісом);
> - **касовий апарат (ПРРО), зареєстрований у ДПС** через кабінет платника —
>   із присвоєним фіскальним номером;
> - **касир** із логіном/паролем або PIN-кодом та **ліцензійний ключ каси**.
>
> На демо-сервері цих реквізитів немає. Тому **Флоу 1 (налаштування)** можна пройти
> наживо повністю, а у **Флоу 2 (робочий день)** усі кнопки дій (`Authenticate`,
> `Open Shift`, `Register Receipt`, `X-Report`, `Close Shift`) звертаються до ДПС
> через Checkbox і без реального підключення повернуть **помилку автентифікації**
> (стан запису → `error`, текст у полі **Error Message**). Нижче для таких кроків
> описано **що ввести і що станеться при реальному підключенні**; «живих» числових
> прикладів із фіскального чека тут свідомо немає.

Меню домену **ПРРО (PRRO)** розташоване всередині українського застосунку обліку
(корінь `l10n_ua_account_base`):

| Пункт меню | Модель | Призначення |
|-----------|--------|-------------|
| **Configurations** | `l10n_ua.prro.config` | Каса ПРРО (провайдер, фіскальний номер, зв'язок з POS) |
| **Checkbox** | `l10n_ua.prro.checkbox.config` | Підключення до сервісу Checkbox (логін касира, ключ) |
| **Shifts** | `l10n_ua.prro.shift` | Зміни каси, X/Z-звіти, підсумки |
| **Receipts** | `l10n_ua.prro.receipt` | Фіскальні чеки (продаж, повернення, службові операції) |

> _Скриншот:_ `00-menu.png` — Меню домену ПРРО

## Флоу 1. Налаштування каси / касира

> Одноразове налаштування каси перед початком роботи. Виконується наживо на демо
> **до** кроку автентифікації (сам вхід касира вимагає реального акаунта).

### Крок 1. Реквізити каси ПРРО

**ПРРО → Configurations → кнопка `Новий`.** Створюється запис
`l10n_ua.prro.config` — провайдер-незалежна конфігурація каси. Заповніть:

| Поле | Значення (приклад) |
|------|--------------------|
| Name | Каса №1 (магазин) |
| Provider | **Checkbox** |
| Fiscal Number | `4000123456` _(фіскальний номер ПРРО з реєстрації в ДПС)_ |
| Company | ТОВ «Тестова Компанія» |
| POS Configurations _(вкладка **POS**)_ | Точка продажу `pos.config`, до якої прив'язана каса |

**Результат введення:** запис збережено, поле **State** = `not_configured`
(касу створено, але Checkbox ще не підключено). Обчислюване поле **Current Shift**
поки порожнє — відкритої зміни немає.

> _Скриншот:_ `01-prro-config.png` — Картка каси ПРРО

### Крок 2. Підключення Checkbox (логін / PIN каси + ліцензійний ключ)

**ПРРО → Checkbox → кнопка `Новий`.** Запис `l10n_ua.prro.checkbox.config`
(з чатером — історією дій) зберігає реквізити доступу до сервісу:

| Поле | Значення (приклад) |
|------|--------------------|
| Name | Підключення каси №1 |
| PRRO Configuration | **Каса №1 (магазин)** _(запис із кроку 1)_ |
| License Key | Ліцензійний ключ каси з Checkbox |
| Authentication Type | **Login and Password** _або_ **PIN Code** |
| Cashier Login / Password | заповнюється для типу `login` |
| Cashier PIN | заповнюється для типу `pin` |

> При зміні **Authentication Type** поля авторизації **очищуються**
> (`_clean_auth_fields`): перехід на PIN стирає логін/пароль, і навпаки.

**Крок 2.1 — Перевірка зв'язку (без токена).** Кнопка **Test Connection**
(`action_test_connection`) викликає `cash-registers/ping-tax-service`.

| Дія | Очікуваний результат |
|-----|----------------------|
| Натиснути **Test Connection** | Повідомлення про доступність сервісу ДПС. Це **єдина** кнопка, що працює **до** входу касира (не потребує токена). |

**Крок 2.2 — Автентифікація касира.** Кнопка **Authenticate**
(`action_authenticate`):

| Дія | Очікуваний результат (при реальному підключенні) |
|-----|--------------------------------------------------|
| Натиснути **Authenticate** | 1. Вхід касира — `POST /cashier/signin` (логін) або `POST /cashier/signinPinCode` (PIN); 2. `access_token` збережено, **Token Expiry** = +1 тиждень; 3. підтягуються дані касира (`cashier/me`) і каси (`cash-registers/info`) — поля **Cash Register ID / Fiscal Number / Name** заповнюються автоматично; 4. **State** → `authenticated`, у чатер — запис про вхід. |
| _На демо_ | **State** → `error`, текст у полі **Error Message** (немає реального акаунта/каси — див. «Передумови»). |

Кнопка **Sign Out** (`action_signout`, `cashier/signout`) виходить із сесії
й обнуляє токен.

> _Скриншот:_ `02-checkbox-config.png` — Картка підключення Checkbox
> _Скриншот:_ `03-checkbox-authenticate.png` — Автентифікація касира

### Крок 3. Результат: каса «активна»

Після успішної автентифікації каса готова до роботи:

| Об'єкт | Стан після налаштування |
|--------|-------------------------|
| `l10n_ua.prro.checkbox.config` | **State** = `authenticated`, токен дійсний 1 тиждень |
| `l10n_ua.prro.config` (каса) | **State** = `active` |
| Реквізити каси | **Cash Register ID / Fiscal Number / Name** заповнені з Checkbox |

> **Синхронізація податків (частково).** Перед початком роботи варто натиснути
> **Sync Taxes** (`action_sync_taxes`, `GET /tax` через `api.get_taxes()`) — підтягує
> перелік актуальних ставок податків із Checkbox.
>
> **Стан реалізації (чесно):** метод **лише отримує перелік** ставок і пише в чатер
> «Synced N tax rates from Checkbox» — і повертає `taxes` (список). **Автоматичного
> мапування отриманих ставок на податки Odoo (`account.tax`) НЕ виконується**:
> ставки нікуди не зберігаються, у рядку чека `l10n_ua.prro.receipt.line` ставка
> задається окремим полем `tax_rate` (просто число %), не пов'язаним із `account.tax`.
> Тобто дія має радше діагностичний характер (перевірити, що Checkbox повертає
> податки), а не наповнює конфігурацію.

## Флоу 2. Робочий день касира

> Наскрізний денний цикл каси: відкрити зміну → чеки продажу → повернення →
> X-звіт → **Z-звіт (закриття зміни)**. Кожна дія звертається до ДПС через Checkbox
> і **вимагає дійсного токена** (Флоу 1, крок 2.2). **На демо кроки цього флоу
> повертають помилку токена** — нижче описано введення й очікуваний результат при
> реальному підключенні.

### Крок 1. Відкрити зміну

Кнопка **Open Shift** (`action_open_shift`):

| Дія | Очікуваний результат |
|-----|----------------------|
| Натиснути **Open Shift** | 1. Перевірка, чи немає вже відкритої зміни (`api.get_shift()`) — якщо є, помилка «Shift is already open»; 2. `POST /shifts` відкриває зміну на боці Checkbox/ДПС; 3. створюється запис `l10n_ua.prro.shift`: **State** = `open`, заповнено **Shift # (serial)** і **Open Date**; 4. у чатер — «Shift #N opened». |

Відкриту зміну видно в **ПРРО → Shifts** (**State** = `Open`) і в полі
**Current Shift** каси.

> _Скриншот:_ `04-shift-open.png` — Відкрита зміна

### Крок 2. Фіскальний чек продажу (позиції, сума, оплата)

Реєстрація чека продажу — метод `action_register_receipt(receipt_data)`,
що викликає `POST /receipts/sell`. Приклад наповнення чека:

| Поле чека / рядка | Значення (приклад) |
|-------------------|--------------------|
| Тип чека | **Sale** (продаж) |
| Рядок 1 → Найменування | Кава мелена 250 г |
| Рядок 1 → UKTZED Code | `0901210000` _(код УКТЗЕД)_ |
| Рядок 1 → Кількість × Ціна | 2 × 180,00 |
| Рядок 1 → Ставка податку | ПДВ 20 % |
| **Subtotal** (рядок) | **360,00** _(обчислюється)_ |
| Оплата | **готівка / картка / змішана** |
| Cash Amount + Card Amount | напр. 360,00 готівкою |

| Дія | Очікуваний результат |
|-----|----------------------|
| Зареєструвати чек | 1. `POST /receipts/sell`; 2. у відповіді — **фіскальний код** (`fiscal_code` → поле **Fiscal Number**), локальний номер (`serial` → **Local Number**); 3. створюється запис `l10n_ua.prro.receipt` типу **Sale**, **State** = `registered`, прив'язаний до поточної зміни; 4. чек з'являється в **ПРРО → Receipts**. |

> **Виправлено (звірено з кодом `action_register_receipt`):** поле **QR Code URL**
> (`qr_code`) **НЕ заповнюється автоматично** при реєстрації чека. Метод створює
> запис лише з полями `fiscal_number`, `local_number`, `receipt_type='sale'`,
> `state='registered'` та `shift_id`. Саме поле `qr_code` у моделі оголошене, але
> жодна дія його не пише (див. Флоу 3, PRRO-17). Раніше цей крок помилково
> стверджував «заповнено QR Code URL» — це неправда.

**Сума чека (issue #186).** `total_amount` — обчислюване й збережене поле
(`_compute_total = cash_amount + card_amount`). Тепер `action_register_receipt`
розкладає платежі відповіді/запиту Checkbox (`_prepare_payment_vals`: `CASH` →
`cash_amount`, `CASHLESS` → `card_amount`, тип оплати cash/card/mixed), тож
`_compute_total` дає **реальну суму**, а не 0. Якщо платіжний поділ не заданий,
сума береться як запасний варіант із **підсумку рядків** (`line_ids.subtotal`).

> **Обмеження (чесно):**
> - Метод створює «шапку» чека, але **рядки з `pos.order` поки не переносяться
>   автоматично** — `line_ids` лишаються порожніми (відомий пункт у планах,
>   див. [опис домену](../prro.md)); тому за наявності платежів сума йде саме з них.

> _Скриншот:_ `05-receipt-sale.png` — Чек продажу
> _Скриншот:_ `06-receipts-list.png` — Список чеків

### Крок 3. Повернення

Тип чека **Return** (`return`) — повертає товар покупцю:

| Дія | Очікуваний результат |
|-----|----------------------|
| Оформити повернення (тип `return`) | Клієнт `CheckboxAPI` викликає `receipts/return`; сума зменшує підсумок **Total Returns** зміни (окремо від **Total Sales**). |

> **Стан реалізації:** ендпоінт `return` присутній у `CheckboxAPI`, але **окрема
> кнопка-дія повернення з боку моделі ще не задіяна** — тип чека `return` можна
> виставити вручну на записі `l10n_ua.prro.receipt`. Повноцінне повернення на боці
> ДПС потребує реального підключення.

**Службові операції з готівкою** (не продаж):

| Дія (метод) | Ендпоінт | Опис |
|-------------|----------|------|
| **Service Input** (`action_service_input`) | `POST /receipts/service` | Службове **внесення** готівки (додатна сума) |
| **Service Output** (`action_service_output`) | `POST /receipts/service` | Службова **видача** готівки (**від'ємна** сума) |

> _Скриншот:_ `07-receipt-return.png` — Повернення / службова операція

### Крок 4. X-звіт (проміжний, без закриття зміни)

Кнопка **X-Report** (`action_x_report`):

| Дія | Очікуваний результат |
|-----|----------------------|
| Натиснути **X-Report** | `POST /reports` формує **X-звіт** — проміжний звіт без закриття зміни; у чатер — «X-Report generated». **Стан зміни НЕ змінюється**, кнопку можна викликати кілька разів за зміну. |

Підсумки зміни на записі `l10n_ua.prro.shift` рахуються **автоматично** з

### Крок 5. Z-звіт (закриття зміни)

## Флоу 3. Межові сценарії та нереалізовані можливості

> Цей блок описує функції, **оголошені в клієнті `CheckboxAPI`, але не доведені
> до робочих дій з боку моделей Odoo**. Наводимо **намір** (як мало би працювати)
> і **поточний стан** (що є в коді насправді), щоб не створювати хибних очікувань.
> Теги: **[ЗАГЛУШКА]** — код-заготовка без виклику; **[НЕ РЕАЛІЗОВАНО]** — немає
> ні кнопки, ні виклику з моделі.

### 3.1. Офлайн-режим і резервування фіскальних номерів — [ЗАГЛУШКА]

**Намір.** ПРРО має вміти працювати без зв'язку з ДПС: заздалегідь зарезервувати
діапазон офлайн фіскальних номерів, перемкнутись у офлайн, пробивати чеки локально
(`sell-offline`), а після відновлення зв'язку — синхронізувати їх із ДПС.

**Поточний стан.** У `CheckboxAPI` є **повний набір** офлайн-ендпоінтів, але
**жоден не викликається з моделі** — немає кнопок, немає збереження офлайн-кодів,
немає автоперемикання online/offline:

| Метод клієнта `CheckboxAPI` | Ендпоінт | Задіяно з моделі? |
|-----------------------------|----------|-------------------|
| `go_offline()` | `POST /cash-registers/go-offline` | ні |
| `go_online()` | `POST /cash-registers/go-online` | ні |
| `create_receipt_offline(receipt_data)` | `POST /receipts/sell-offline` | ні |
| `ask_offline_codes(count)` | `GET /cash-registers/ask-offline-codes` | ні |
| `get_offline_codes()` | `GET /cash-registers/get-offline-codes` | ні |
| `get_offline_time()` | `GET /cash-registers/get-offline-time` | ні |

Ані `l10n_ua.prro.config`, ані `l10n_ua.prro.checkbox.config` не мають полів для
зберігання зарезервованих офлайн-кодів чи прапорця офлайн-стану. Офлайн-режим —
**фактично заглушка на рівні клієнта**, а не робочий сценарій. Це найбільша
прогалина щодо вимоги безперервності фіскалізації (наказ Мінфіну щодо офлайн-ПРРО,
орієнтовно №329 від 23.06.2020).

> _Скриншот:_ `10-offline-stub.png` — (немає UI: офлайн-режим не виведено в інтерфейс)

### 3.2. Скасування / сторнування чека та error-стан

**Стани чека.** Модель `l10n_ua.prro.receipt` має поле `state` лише зі значеннями
`draft → registered → error`. **Окремого стану «сторновано»/«скасовано» немає**,
і **немає методу `action_cancel`** чи сторнування.

**Як скасувати помилковий чек.** Фіскально помилковий чек «гаситься»
**окремим чеком повернення** (див. Флоу 2, крок 3 / PRRO-9), а не зміною стану
початкового запису. Тобто сторнування = новий чек `receipt_type='return'`.

**Error-стан (працює).** Будь-яка дія при винятку викликає `_set_error(message)`:

| Крок | Що відбувається |
|------|-----------------|
| 1 | Виняток у виклику API (тайм-аут, помилка ДПС, немає токена) |
| 2 | `_set_error` пише `state = 'error'` та текст у `error_message` |
| 3 | Виняток **перевикидається** користувачу (`raise`) — касир бачить причину |
| 4 | Наступна успішна дія викликає `_clear_error()` (обнуляє `error_message`) |

> **Важливо:** `state='error'` існує на `l10n_ua.prro.checkbox.config` (підключення)
> і на `l10n_ua.prro.receipt` (чек). Помилка **дії** підключення переводить у `error`
> сам запис підключення, а не окремий чек.

> _Скриншот:_ `11-error-state.png` — Запис у стані `error` з текстом Error Message

### 3.3. Звірка з ДПС і пошук чека — [НЕ РЕАЛІЗОВАНО в UI]

**Намір.** Бухгалтер/старший касир має звіряти дані Odoo з фіскальним сервером:
знайти чек за параметрами, отримати картку чека чи інформацію про зміну.

**Поточний стан.** `CheckboxAPI` надає методи звірки, але **жодного не виведено
в UI — кнопок звірки немає**:

| Метод клієнта | Ендпоінт | Задіяно з моделі? |
|---------------|----------|-------------------|
| `search_receipts(params)` | `GET /receipts/search` | ні |
| `get_receipt(receipt_id)` | `GET /receipts/{id}` | ні |
| `get_shift_info(shift_id)` | `GET /shifts/{id}` | ні |
| `ping_tax_service()` | `POST /cash-registers/ping-tax-service` | **так** (Test Connection) |

Практично звірка робиться **вручну**: підсумки зміни в Odoo (`total_sales`,
`total_returns`, `total_cash`, `total_card`, `receipt_count` — обчислені
`_compute_totals`) порівнюються з кабінетом Checkbox/ДПС очима. Власного каналу
передавання даних до ДПС Odoo не має — це робить сам сервіс Checkbox як
інтегрований ПРРО.

> _Скриншот:_ `12-reconcile-manual.png` — (немає UI: пошук/звірка не виведені)

### 3.4. Друковані формати чека (text / HTML / PNG) і QR — [НЕ РЕАЛІЗОВАНО]

**Намір.** Видати покупцю чек — паперово (text/PNG) чи електронно (HTML/QR),
а поле `qr_code` заповнити URL для перевірки чека в кабінеті ДПС (вимога наказу
Мінфіну №13).

**Поточний стан.** `CheckboxAPI` вміє отримати чек у чотирьох форматах, але
**з боку моделі жоден не викликається** — немає ні кнопок друку, ні заповнення
`qr_code`:

| Метод клієнта | Ендпоінт | Повертає | Задіяно з моделі? |
|---------------|----------|----------|-------------------|
| `get_receipt_text(id)` | `GET /receipts/{id}/text` | текст (UTF-8) | ні |
| `get_receipt_html(id)` | `GET /receipts/{id}/html` | HTML | ні |
| `get_receipt_png(id, width)` | `GET /receipts/{id}/png` | PNG (bytes) | ні |
| `get_receipt_qrcode(id)` | `GET /receipts/{id}/qrcode` | QR (bytes) | ні |

Поле `qr_code` (**QR Code URL**) у `l10n_ua.prro.receipt` існує, але
**лишається порожнім** — це і є першопричина виправлення у Флоу 2, крок 2. Друку
або електронної видачі чека покупцю поки немає.

> _Скриншот:_ `13-print-formats.png` — (немає UI: друковані формати не виведені)

### 3.5. Тайм-аути й обробка помилок API (деталізація PRRO-18)

Усі запити проходять через `CheckboxAPI._request`:

| Аспект | Реалізація |
|--------|-----------|
| Тайм-аут | **захардкоджено `REQUEST_TIMEOUT = 30` секунд** (у коді позначено `TODO` винести в налаштування; для деяких операцій 30 с замало) |
| `requests.exceptions.Timeout` | → `UserError` «Checkbox API timeout. Please try again.» |
| `requests.exceptions.ConnectionError` | → `UserError` «Cannot connect to Checkbox API…» |
| HTTP 4xx/5xx | розбирає `_handle_error`: бере `detail` (рядок або список `msg`) чи `message` з JSON; якщо тіло не JSON — «Checkbox API error (code): text» |
| Успіх без JSON | `response.json()` при `JSONDecodeError` → повертає `response.text` |

Далі будь-яка дія моделі перехоплює виняток, викликає `_set_error` (стан `error`
+ `error_message`) і **перевикидає** — тож касир завжди бачить причину відмови
фіскалізації. Прямі виклики форматів (`get_receipt_text/html/png/qrcode`,
`get_report_text`) ідуть **повз** `_request` (окремі `requests.get`) — вони теж
з тайм-аутом 30 с, але **без** централізованого `_handle_error`.
