# HOWTO: ПРРО (фіскалізація)

← [Назад до документації](../../README.md) · [Опис домену](../prro.md)

> Покроковий сценарій налаштування програмного РРО через хмарний сервіс
> **Checkbox**, звірений на **[demo.ndev.online](https://demo.ndev.online)**
> (компанія _ТОВ «Тестова Компанія»_). Демо-дані **не видаляються** — конфігурацію
> можна створювати й переналаштовувати під час тестування.

Скріншоти — у теці [`img/prro/`](img/prro/).

---

## Передумови (зовнішнє підключення)

> **ВАЖЛИВО.** Модулі `l10n_ua_prro_base` та `l10n_ua_prro_checkbox` реалізують
> клієнт до API Checkbox (`https://api.checkbox.in.ua/api/v1/`), але **самі по собі
> нічого не фіскалізують**. Щоб реально відкрити зміну, зареєструвати чек чи
> сформувати Z-звіт, потрібні:
>
> - **діючий акаунт Checkbox** (юрособа/ФОП, договір із сервісом);
> - **касовий апарат (ПРРО), зареєстрований у ДПС** через кабінет платника —
>   із фіскальним номером;
> - **касир** із логіном/паролем або PIN-кодом та **ліцензійний ключ каси**.
>
> На демо-сервері цих реквізитів немає, тому **виконати фіскалізацію наживо
> неможливо** — усі кнопки дій (`Authenticate`, `Open Shift`, `Register Receipt`,
> `X-Report`, `Close Shift`) звертаються до ДПС через Checkbox і без реального
> підключення повернуть помилку автентифікації. Нижче описано **як налаштувати
> й що станеться при кожному кроці**; числових прикладів із «живого» чека тут
> свідомо немає.

## 0. Застосунок і меню

Меню домену **ПРРО (PRRO)** розташоване всередині українського застосунку обліку
(корінь `l10n_ua_account_base`). Пункти меню:

| Пункт меню | Модель | Призначення |
|-----------|--------|-------------|
| **Configurations** | `l10n_ua.prro.config` | Налаштування каси ПРРО (провайдер, фіскальний номер, зв'язок з POS) |
| **Shifts** | `l10n_ua.prro.shift` | Зміни каси, X/Z-звіти, підсумки |
| **Receipts** | `l10n_ua.prro.receipt` | Фіскальні чеки (продаж, повернення, службові операції) |
| **Checkbox** | `l10n_ua.prro.checkbox.config` | Підключення до сервісу Checkbox (логін касира, ключ) |

> _Скриншот:_ `00-menu.png`

---

## 1. Налаштування каси ПРРО

**ПРРО → Configurations → Новий.** Створюється запис `l10n_ua.prro.config` —
провайдер-незалежна конфігурація каси:

| Поле | Опис |
|------|------|
| **Name** | Назва каси (довільна) |
| **Provider** | Провайдер: `Checkbox` / `Vchasno Kasa` / `Other` (для нашого флоу — **Checkbox**) |
| **Fiscal Number** | Фіскальний номер ПРРО, отриманий при реєстрації каси в ДПС |
| **Company** | Компанія (для мультикомпанійної бази) |
| **POS Configurations** | Вкладка **POS** — зв'язок з однією або кількома точками продажу `pos.config` |

Стан конфігурації (поле **State**): `not_configured` → `configured` → `active`
(або `error`). Обчислюване поле **Current Shift** показує відкриту зміну цієї каси,
якщо така є.

> _Скриншот:_ `01-prro-config.png`

---

## 2. Підключення Checkbox (касир і ключ)

**ПРРО → Checkbox → Новий.** Запис `l10n_ua.prro.checkbox.config` містить чатер
(історію дій) і реквізити доступу до сервісу:

| Поле | Опис |
|------|------|
| **Name** | Назва підключення |
| **PRRO Configuration** | Посилання на касу з кроку 1 (`l10n_ua.prro.config`) |
| **License Key** | Ліцензійний ключ каси з Checkbox |
| **Authentication Type** | Тип входу касира: **Login and Password** або **PIN Code** |
| **Cashier Login / Password** | Для типу `login` |
| **Cashier PIN** | Для типу `pin` |

Поля авторизації **очищуються при зміні типу входу** (`_clean_auth_fields`): при
переході на PIN стираються логін/пароль, і навпаки.

### 2.1. Перевірка зв'язку

Кнопка **Test Connection** (`action_test_connection`) викликає
`cash-registers/ping-tax-service` — перевіряє доступність сервісу ДПС. Це єдина
кнопка, що **не потребує токена** (працює до входу касира).

### 2.2. Автентифікація касира

Кнопка **Authenticate** (`action_authenticate`):

1. Вхід касира — `POST /cashier/signin` (логін/пароль) або
   `POST /cashier/signinPinCode` (PIN);
2. `access_token` зберігається з терміном дії **1 тиждень** (поле **Token Expiry**);
3. Підтягуються дані касира (`cashier/me`) та каси (`cash-registers/info`) —
   поля **Cash Register ID / Fiscal Number / Name** заповнюються автоматично;
4. Стан переходить у **authenticated**, у чатер пишеться запис про вхід.

Кнопка **Sign Out** (`action_signout`) виходить із сесії й обнуляє токен.

> **На демо** цей крок поверне помилку автентифікації (немає реального акаунта/каси) —
> див. розділ «Передумови». Стан запису стане **error**, а текст помилки з'явиться
> в полі **Error Message**.

> _Скриншоти:_ `02-checkbox-config.png`, `03-checkbox-authenticate.png`

---

## 3. Відкриття зміни

Кнопка **Open Shift** (`action_open_shift`, вимагає токена):

1. Перевіряє, чи немає вже відкритої зміни (`api.get_shift()`) — якщо є, кидає
   помилку «Shift is already open»;
2. `POST /shifts` відкриває зміну на боці Checkbox/ДПС;
3. Створюється запис `l10n_ua.prro.shift` зі станом **open**, номером зміни
   (`serial`) і датою відкриття;
4. У чатер пишеться «Shift #N opened».

Відкриту зміну видно у **ПРРО → Shifts** (стан **Open**) та в полі
**Current Shift** каси.

> _Скриншот:_ `04-shift-open.png`

## 4. Фіскальний чек (продаж) → реєстрація в ДПС

Реєстрація чека продажу — метод `action_register_receipt(receipt_data)`, що
викликає `POST /receipts/sell`. За успіху:

- у відповіді приходять **фіскальний код** (`fiscal_code`), локальний номер
  (`serial`) і сума (`total_sum`, у копійках → ділиться на 100);
- створюється запис `l10n_ua.prro.receipt` типу **Sale** зі станом **registered**,
  прив'язаний до поточної зміни;
- чек з'являється у **ПРРО → Receipts**.

Модель чека (`l10n_ua.prro.receipt`) підтримує типи оплати
**готівка / картка / змішана** (сума = `cash_amount + card_amount`), поле
**QR Code URL** та рядки чека (`l10n_ua.prro.receipt.line`) з полями
**UKTZED Code** (код УКТЗЕД), кількість, ціна, знижка %, ставка податку та
обчислюваний **Subtotal**.

> **Обмеження (чесно):** метод реєстрації створює «шапку» чека, але **рядки з
> `pos.order` поки не переносяться автоматично** — це відомий пункт у планах
> (див. [опис домену](../prro.md)). На демо крок повертає помилку токена.

> _Скриншоти:_ `05-receipt-sale.png`, `06-receipts-list.png`

## 5. Повернення

Тип чека **Return** (`return`) передбачений моделлю `l10n_ua.prro.receipt`, а
клієнт `CheckboxAPI` має відповідний ендпоінт `receipts/return`. Повернення
зменшує підсумок **Total Returns** у зміні (окремо від **Total Sales**).

> **Стан реалізації:** ендпоінт `return` присутній у `CheckboxAPI`, але **окрема
> кнопка-дія повернення з боку моделі ще не задіяна** — тип чека можна виставити
> вручну на записі `l10n_ua.prro.receipt`. Повноцінне повернення на боці ДПС
> потребує реального підключення.

Службові операції з готівкою (не продаж):

- **Service Input** (`action_service_input`) — службове внесення готівки,
  `POST /receipts/service` з додатною сумою;
- **Service Output** (`action_service_output`) — службова видача, той самий
  ендпоінт із **від'ємною** сумою.

> _Скриншот:_ `07-receipt-return.png`

## 6. X-звіт

Кнопка **X-Report** (`action_x_report`, вимагає токена) викликає
`POST /reports` — формує **X-звіт** (проміжний звіт без закриття зміни). У чатер
пишеться «X-Report generated». X-звіт не змінює стану зміни й може викликатися
кілька разів за зміну.

Підсумки зміни (кількість чеків, продажі/повернення, готівка/картка) рахуються
на записі `l10n_ua.prro.shift` автоматично з прив'язаних чеків.

> _Скриншот:_ `08-x-report.png`

---

## 7. Z-звіт (закриття зміни)

Кнопка **Close Shift (Z-Report)** (`action_close_shift`, вимагає токена):

1. `POST /shifts/close` закриває зміну на боці Checkbox/ДПС;
2. з відповіді береться **номер Z-звіту** (`z_report.serial`);
3. запис `l10n_ua.prro.shift` переходить у стан **closed**, заповнюються
   **Close Date** та **Z-Report Number**;
4. у чатер пишеться «Shift closed. Z-Report #N».

Після Z-звіту зміну закрито; для нових продажів потрібно **відкрити нову зміну**
(крок 3).

> **Синхронізація податків.** Кнопка **Sync Taxes** (`action_sync_taxes`,
> `GET /tax`) підтягує актуальні ставки податків із Checkbox — корисно перед
> початком роботи каси.

> _Скриншот:_ `09-z-report.png`
