## Поточний стан

> Прочитайте цей розділ **першим** — він визначає, що реально працює, а що ні.

| Функція | Стан |
|---------|------|
| Базові поля перевізника (`delivery.carrier`) | 🟢 реалізовано |
| Довідник відділень / поштоматів (`l10n_ua.delivery.warehouse`) | 🟢 реалізовано |
| Посилання на відстеження (tracking link) | 🟢 формується як URL із `carrier_tracking_ref` |
| Розрахунок вартості доставки | 🟡 заглушка — повертає `price = 0.0` |
| Створення ТТН / накладної | 🟡 заглушка — порожній `tracking_number` |
| Скасування ТТН | 🟡 заглушка — `pass` |
| Синхронізація довідника відділень з API | 🟡 заглушка — `# TODO`, `pass` |
| Друк маркування | 🟡 не реалізовано |

**Що це означає на практиці:**

- Модулі `l10n_ua_delivery_novaposhta`, `l10n_ua_delivery_ukrposhta`, `l10n_ua_delivery_meest`
  **не роблять реальних викликів API** перевізників. Усі методи створення відправлень,
  розрахунку вартості та синхронізації містять `# TODO` і повертають нульові / порожні значення.
- Абстрактний mixin `l10n_ua.delivery.mixin` описує лише **інтерфейс** (`ua_create_shipment`,
  `ua_get_tracking`, `ua_calculate_cost`, `ua_get_warehouses`, `ua_print_label`) — усі його
  методи викидають `NotImplementedError`.
- Автоматизованих тестів у домені **немає**.
- Єдине, що працює «наскрізь», — формування **посилання на відстеження**: якщо у відвантаженні
  вручну заповнити номер ТТН (`carrier_tracking_ref`), система збудує коректний URL на трекінг
  перевізника.

Отже, домен придатний для **налаштування перевізників і ведення довідника відділень**; фактичну
ТТН поки що доводиться створювати в кабінеті перевізника й вносити її номер у відвантаження
вручну. Нижче — **Флоу 1** (повністю робочий), **Флоу 2** (планований — створення ТТН/трекінг) та
**Флоу 3–10** (окремі сценарії: друк маркування, трекінг-крон, COD, Укрпошта, Meest, повернення,
порівняння тарифів, валідація ваги). Кожен флоу позначено `[РЕАЛІЗОВАНО]` / `[ЧАСТКОВО]` /
`[ЗАГЛУШКА]`; кроки з викликами API не виконуються автоматично.

> _Скриншот меню:_ `00-menu.png`

Функціонал доставки розподілений між двома місцями:

- **Склад → Конфігурація → Способи доставки** (стандартні перевізники Odoo, `delivery.carrier`) —
  тут задаються українські поля перевізника;
- **меню `Delivery` (Доставка)** в українському кореневому меню (`l10n_ua_account_base`) →
  **Warehouses (Відділення)** — довідник відділень / поштоматів.

## Флоу 1. Налаштування перевізника

> Повністю робочий процес: створення способу доставки з українськими полями та наповнення
> довідника відділень. Результат — перевізник доступний для вибору у відвантаженнях і продажах.

### Крок 1. Створити спосіб доставки та заповнити базові поля перевізника

**Склад → Конфігурація → Способи доставки → кнопка `Новий`.** Створіть спосіб доставки для
потрібного перевізника (Нова Пошта / Укрпошта / Meest). Модуль `l10n_ua_delivery_base` додає до
картки українські поля конфігурації:

| Поле | Призначення |
|------|-------------|
| `ua_carrier_type` — тип перевізника | `novaposhta` / `meest` / `ukrposhta` |
| `ua_api_key` — ключ API | ключ доступу до API перевізника |
| `ua_sender_ref` — референс відправника | ID відправника в системі перевізника |
| `ua_sender_address_ref` — референс адреси | ID адреси відправника |
| `ua_sender_contact_ref` — референс контакту | ID контакту відправника |
| `ua_default_service_type` — тип послуги | склад-склад / склад-двері / двері-склад / двері-двері (за замовч. `warehouse`) |
| `ua_default_payment_method` — платник | відправник / отримувач / третя сторона (за замовч. `sender`) |
| `ua_cod_enabled` — післяплата (COD) | увімкнення накладеного платежу |

Модуль **Нова Пошта** додатково додає поле `np_api_url` (за замовчуванням
`https://api.novaposhta.ua/v2.0/json/`). Модулі **Укрпошта** та **Meest** власних полів до картки
перевізника не додають.

> **Зверніть увагу:** заповнення `ua_api_key` та референсів **не активує** обмін із перевізником —
> код, що мав би використати ці значення для викликів API, наразі є заглушкою (див.
> [«Поточний стан»](#поточний-стан)). Поля існують як заготовка під майбутню інтеграцію.

> _Скриншот:_ `01-carrier-config.png`

### Крок 2. Наповнити довідник відділень / поштоматів

**Delivery (Доставка) → Warehouses (Відділення) → кнопка `Новий`.** Модель
`l10n_ua.delivery.warehouse` — спільний довідник відділень і поштоматів для всіх перевізників.
Це **повністю робоча** частина домену. Поля запису:

| Поле | Призначення |
|------|-------------|
| `name` | назва відділення |
| `carrier_type` | до якого перевізника належить |
| `warehouse_ref` | референс у системі перевізника |
| `warehouse_number` | номер відділення |
| `warehouse_type` | тип: склад / поштомат / вантажний |
| `city`, `city_ref` | місто та його референс |
| `address`, `phone`, `schedule` | адреса, телефон, графік |
| `max_weight` | максимальна вага |
| `latitude`, `longitude` | координати |
| `active` | активність |

Особливості довідника:

- обмеження унікальності `UNIQUE(warehouse_ref, carrier_type)` — одне відділення на перевізника
  не дублюється;
- кастомний пошук (`name_search`) працює за **назвою, номером відділення та містом** — зручно
  вибирати відділення у полях типу «куди доставити».

> **Наповнення (ручний імпорт — DLV-4, DLV-5).** `[ЧАСТКОВО]` Оскільки автоматична синхронізація
> з API — заглушка, відділення поки що **вносяться вручну** (кнопка `Новий`) або через стандартний
> імпорт списку Odoo (кнопка `⚙️ Дії → Імпорт записів`, CSV/XLSX з колонками `name`, `carrier_type`,
> `warehouse_ref`, `warehouse_number`, `city`, `address`, `max_weight` тощо). Особливості стану
> синхронізації по перевізниках:
>
> - **Нова Пошта:** у формі перевізника є кнопка `Sync Warehouses` (`np_sync_warehouses`). За
>   задумом вона мала б звертатися до `Address.getWarehouses` API НП і робити upsert у
>   `l10n_ua.delivery.warehouse` за `warehouse_ref`. Фактично метод — `# TODO` + `pass`: **нічого
>   не завантажує**, помилки теж не показує. Не покладайтеся на неї.
> - **Укрпошта:** метод `ukrposhta_sync_branches` існує, але **кнопки у формі перевізника немає**
>   взагалі — синхронізацію нема звідки запустити.
> - **Meest:** метод `meest_sync_warehouses` так само порожній і **без кнопки** — довідник
>   відділень Meest наповнюється лише руками.
>
> _Стан:_ 🟡 сам довідник і пошук працюють (DLV-3, DLV-4); наповнення з API — заглушка (DLV-5).
> Практичний висновок: підготуйте CSV відділень (наприклад, вивантажений з кабінету перевізника)
> і залийте його імпортом — це єдиний робочий спосіб заповнити таблицю сьогодні.

> _Скриншоти:_ `02-warehouses-list.png`, `03-warehouse-form.png`, `05-import-warehouses.png`

### Результат

Перевізник із заповненими українськими полями та довідник відділень доступні для вибору у
відвантаженнях (`stock.picking`) і продажах. Номер ТТН у поле відстеження поки вноситься вручну
(див. Флоу 2).

## Флоу 2. (планований) Створення ТТН / відстеження

> **Проєктний задум** флоу — як воно має працювати після реалізації інтеграцій, щоб було
> зрозуміло призначення полів. Наразі кроки з викликами API **не виконуються автоматично**;
> позначки стану показують, що реально працює вже сьогодні.

### Крок 1. Розрахунок вартості доставки (DLV-6) `[ЗАГЛУШКА]`

При оформленні продажу / відвантаження ядро `delivery` викликає `delivery.carrier.rate_shipment()`,
який делегує на `np_rate_shipment(order)` (аналогічно `ukrposhta_rate_shipment` / `meest_rate_shipment`).
За задумом НП мала б звертатися до `InternetDocument.getDocumentPrice` (вага, оголошена вартість,
міста відправника/одержувача, тип сервісу). Фактично метод містить `# TODO` і повертає
`{'success': True, 'price': 0.0, ...}`.
_Стан:_ 🟡 заглушка — **вартість завжди `0.0` грн**, а не реальний тариф. У кошику продажу рядок
доставки додасться з нульовою ціною; фактичну вартість дізнавайтеся в кабінеті/калькуляторі
перевізника й за потреби проставляйте вручну.

### Крок 2. Створення ТТН / накладної (DLV-7) `[ЗАГЛУШКА]`

При підтвердженні відвантаження (`stock.picking`) ядро `delivery` викликає `send_shipping`, який
делегує на `np_send_shipping(pickings)` (аналогічно `ukrposhta_send_shipping` / `meest_send_shipping`).
За задумом НП мала б викликати `InternetDocument.save`, записати номер у `picking.carrier_tracking_ref`
і повернути `exact_price`. Фактично метод повертає `[{'exact_price': 0.0, 'tracking_number': ''}]`.

**Що реально працює vs через кабінет:**
- ❌ автоматична генерація номера ТТН у Odoo — **не працює** (порожній `tracking_number`);
- ✅ поле `carrier_tracking_ref` у відвантаженні редагується вручну, і щойно ви впишете туди номер
  ТТН, створений у кабінеті перевізника, коректно спрацює трекінг-посилання (Крок 4).

_Стан:_ 🟡 заглушка → **робочий обхід:** створіть ТТН у кабінеті НП/Укрпошти/Meest і внесіть її
номер у `carrier_tracking_ref` вручну.

### Крок 3. Друк маркування

Формування етикетки перевізника (`ua_print_label`).
_Стан:_ 🟡 не реалізовано.

### Крок 4. Відстеження (працює вже сьогодні)

За номером ТТН система будує посилання на трекінг перевізника
(`np_get_tracking_link` / `ukrposhta_get_tracking_link` / `meest_get_tracking_link`).
_Стан:_ 🟢 **працює** — щойно заповните `carrier_tracking_ref`, отримаєте коректний URL.

### Крок 5. Скасування ТТН

Скасування раніше створеної накладної (`*_cancel_shipment`).
_Стан:_ 🟡 заглушка, `pass`.

### Результат / робочий обхідний варіант сьогодні

Створіть ТТН у кабінеті перевізника, впишіть її номер у поле відстеження відвантаження
(`carrier_tracking_ref`) — і посилання на трекінг (Крок 4) сформується коректно. Розрахунок
вартості, автоматичне створення ТТН, друк маркування та скасування наживо поки недоступні.

> _Скриншот:_ `04-tracking-link.png`

## Флоу 3. Друк маркування / наклейки (DLV-8) `[ЗАГЛУШКА]`

> Після створення ТТН комірник має отримати PDF-наклейку (маркування ~100×100 з номером ТТН,
> штрих-кодом, ПІБ одержувача, містом і відділенням) для наклеювання на посилку.

**Цільовий флоу:** зі сформованого відвантаження — кнопка друку наклейки → міксин
`l10n_ua.delivery.mixin.ua_print_label(picking)` генерує PDF-етикетку перевізника.

_Стан:_ 🟡 **заглушка.** Метод `ua_print_label(picking)` у міксині викидає `NotImplementedError()`.
В окремих модулях перевізників (`np_*`, `ukrposhta_*`, `meest_*`) власного методу друку наклейки
**немає взагалі** — жодного QWeb-звіту чи виклику генерації PDF. Наклейку сьогодні друкуйте в
кабінеті перевізника.

> _Скриншот:_ `06-print-label.png`

## Флоу 4. Автоматичне оновлення статусу / трекінг-крон (DLV-10) `[ЗАГЛУШКА]`

> Періодичне підтягування статусу посилки («в дорозі», «прибула у відділення», «вручено»,
> «повернення») без ручних дій оператора.

**Цільовий флоу:** крон-завдання проходить по відкритих відвантаженнях із заповненим
`carrier_tracking_ref`, викликає `ua_get_tracking(tracking_number)` міксину (для НП —
`TrackingDocument.getStatusDocuments`) і оновлює статус посилки.

_Стан:_ 🟡 **заглушка.** Метод `ua_get_tracking(tracking_number)` викидає `NotImplementedError()`;
**крон-завдання періодичного трекінгу в домені немає** (жодного `ir.cron` у `data/`). Статуси
посилок автоматично не оновлюються.

**Важливо — не плутати з посиланням трекінгу.** Формування *URL* трекінгу (`*_get_tracking_link`)
працює (див. Флоу 2, Крок 4), але це лише посилання «відкрити на сайті перевізника» — воно **не
підтягує** статус усередину Odoo. Статус наразі перевіряється лише вручну, перейшовши за посиланням.

> _Скриншот:_ `07-tracking-cron.png`

## Флоу 5. Накладений платіж (COD): сума та повернення (DLV-11) `[ЗАГЛУШКА]`

> Продаж із післяплатою: одержувач платить за товар при отриманні, перевізник переказує суму
> назад на рахунок продавця.

**Цільовий флоу:** на перевізнику вмикається `ua_cod_enabled=True`, `ua_default_payment_method`
визначає платника доставки; при створенні ТТН у перевізника передається сума накладеного платежу
(для НП — `BackwardDeliveryData`), потім відстежується зворотне повернення коштів і звіряється з
`sale.order`.

_Стан:_ 🟡 **заглушка.** Реально існує лише прапорець `ua_cod_enabled` (`fields.Boolean` на
`delivery.carrier`) та вибір платника `ua_default_payment_method` (`sender` / `recipient` /
`third_party`). **Полів для суми накладеного платежу та обліку його повернення в моделях немає**,
а оскільки `*_send_shipping` — заглушка, сума COD у перевізника не передається. Каса/РРО не
задіяні. Практично: вмикати прапорець можна, але сам COD доводиться вести в кабінеті перевізника.

> _Скриншот:_ `08-cod-settings.png`

## Флоу 6. Укрпошта: індекси та адресна доставка (DLV-12) `[ЗАГЛУШКА]`

> Специфіка Укрпошти: відправлення адресуються за **поштовим індексом** (5 цифр), є розділення на
> доставку до відділення й **адресну** доставку (за вулицею/будинком), окремий формат штрих-коду.

**Цільовий флоу:** перевізник із `ua_carrier_type='ukrposhta'` → `ukrposhta_send_shipping` формує
відправлення через Ukrposhta API (модель `Shipment`) з урахуванням індексу та типу доставки.

_Стан:_ 🟡 **заглушка.** `ukrposhta_send_shipping` повертає порожній `tracking_number`; специфіка
Укрпошти не реалізована. **Окремого поля поштового індексу в моделях немає** — у довіднику
`l10n_ua.delivery.warehouse` є лише узагальнене `warehouse_number` (номер відділення), яке під
5-значний індекс не заточене. Розділення адресна/до відділення тримається на загальному
`ua_default_service_type`, без окремої структурованої адреси. Працює лише посилання трекінгу
`ukrposhta_get_tracking_link` → `https://track.ukrposhta.ua/tracking_UA.html?barcode=<ref>`.

> _Скриншот:_ `09-ukrposhta.png`

## Флоу 7. Meest: специфіка перевізника (DLV-13) `[ЗАГЛУШКА]`

> Meest як окремий перевізник (`ua_carrier_type='meest'`) зі своїм API та довідником відділень.

**Цільовий флоу:** розрахунок (`meest_rate_shipment`), створення відправлення (`meest_send_shipping`)
та синхронізація відділень (`meest_sync_warehouses`) через Meest API.

_Стан:_ 🟡 **заглушка.** Усі три методи повертають заглушки або `pass`: `meest_rate_shipment` →
`price=0.0`, `meest_send_shipping` → `tracking_number=''`, `meest_sync_warehouses` → `# TODO`/`pass`
(до того ж **без кнопки** синхронізації у формі). Модуль Meest **не додає власних полів** до картки
`delivery.carrier` (на відміну від НП з `np_api_url`). Довідник відділень Meest наповнюється лише
вручну/імпортом. Працює тільки посилання трекінгу `meest_get_tracking_link` →
`https://meest.ua/tracking?number=<ref>`.

> _Скриншот:_ `10-meest.png`

## Флоу 8. Повернення / скасування відправлення (DLV-14) `[ЗАГЛУШКА]`

> Два сценарії: (а) **скасувати** щойно створену ТТН (помилка в замовленні); (б) **зворотна
> доставка** — повернення товару споживачем назад продавцю.

**Цільовий флоу:**
- скасування ТТН — `np_cancel_shipment` / `ukrposhta_cancel_shipment` / `meest_cancel_shipment`;
- повернення — окрема зворотна ТТН (тип сервісу у зворотному напрямку, `BackwardDelivery` для НП).

_Стан:_ 🟡 **заглушка.** Усі три методи `*_cancel_shipment` містять лише `pass` — скасування ТТН у
перевізника не відбувається. **Спеціального методу створення зворотної (return) ТТН немає взагалі.**
Практично: і скасування, і повернення оформлюються в кабінеті перевізника, а в Odoo відвантаження
редагується/скасовується стандартними засобами `stock.picking`.

> _Скриншот:_ `11-cancel-return.png`

## Флоу 9. Порівняння перевізників за ціною (DLV-16) `[ЗАГЛУШКА]`

> Для одного `sale.order` менеджер хоче порівняти тарифи кількох перевізників (НП / Укрпошта /
> Meest) і обрати найдешевший.

**Цільовий флоу:** по кожному `delivery.carrier` викликається `rate_shipment` → повертає ціну →
менеджер (або автологіка) обирає найвигіднішого.

_Стан:_ 🟡 **заглушка.** Оскільки всі `*_rate_shipment` повертають `price=0.0` (див. DLV-6),
**порівняння беззмістовне — усі перевізники «безкоштовні»**. Автовибір найвигіднішого перевізника
не реалізовано. До реалізації розрахунку тарифів порівнюйте вартість поза системою.

## Флоу 10. Валідація ваги / max_weight (DLV-17) `[ЧАСТКОВО]`

> Поштомат і кожне відділення мають обмеження за вагою; відправлення понад ліміт приймати не можна.

**Цільовий флоу:** перед створенням ТТН система звіряє вагу відправлення з `max_weight`
відділення-одержувача (особливо для `warehouse_type='postomat'` із жорсткими габаритами) і блокує
перевищення.

_Стан:_ 🟡 **частково.** Дані **зберігаються**: у довіднику `l10n_ua.delivery.warehouse` є
`max_weight` (`fields.Float`, кг) і `warehouse_type` (`warehouse` / `postomat` / `cargo`). Проте
**жодна логіка (constraint чи перевірка при `send_shipping`) не звіряє** вагу/габарити відправлення
проти `max_weight` — валідації немає. Оператор мусить контролювати ліміт вручну, орієнтуючись на
значення `max_weight` у картці відділення.

> _Скриншот:_ `12-max-weight.png`
