# Тестові сценарії блоку доставки (служби доставки)

Домен інтегрує українські служби доставки (Нова Пошта, Укрпошта, Meest) зі стандартними
модулями Odoo `sale` та `stock` через ядро `delivery`. Архітектура: базовий модуль
`l10n_ua_delivery_base` розширює `delivery.carrier` (тип перевізника, API-ключі, референси
відправника, тип сервісу, спосіб оплати, накладений платіж), додає довідник відділень
`l10n_ua.delivery.warehouse` та абстрактний міксин `l10n_ua.delivery.mixin`. Три модулі-перевізники
(`l10n_ua_delivery_novaposhta`, `l10n_ua_delivery_ukrposhta`, `l10n_ua_delivery_meest`) успадковують
`delivery.carrier` і мають реалізувати методи розрахунку/створення/трекінгу/друку.

Ролі: **менеджер з логістики** (налаштування перевізників, референси відправника, ціноутворення),
**комірник** (`stock.group_stock_user`/`stock.group_stock_manager` — формування відвантажень, ТТН,
друк маркування), **оператор** (обробка замовлень, вибір міста/відділення одержувача, накладений платіж).

> **КРИТИЧНО — стан реалізації.** Станом на дату аудиту домен є **каркасом (scaffolding)**. Реальні
> HTTP-виклики до API перевізників **відсутні**: усі методи `*_rate_shipment`, `*_send_shipping`,
> `*_cancel_shipment`, `*_sync_warehouses`/`*_sync_branches` містять коментар `# TODO` і повертають
> заглушкові значення (`price=0.0`, `tracking_number=''`, `pass`). Реально працює лише генерація
> посилань трекінгу (`*_get_tracking_link` — просте формування URL). Методи міксину
> (`ua_create_shipment`, `ua_get_tracking`, `ua_calculate_cost`, `ua_get_warehouses`, `ua_print_label`)
> викидають `NotImplementedError()`. Наведені нижче flow описують **цільову поведінку** (як має
> працювати), і для кожного явно позначено `[РЕАЛІЗОВАНО]`, `[ЧАСТКОВО]` або `[ЗАГЛУШКА]`.

---

Flow DLV-1 — Налаштування перевізника Нова Пошта. `[ЧАСТКОВО]` Менеджер з логістики створює запис
`delivery.carrier` → `delivery_type` стандартний, `ua_carrier_type='novaposhta'` → на вкладці «UA Settings»
(видима лише коли `ua_carrier_type` заповнено) вводить `ua_api_key` (поле `password="True"`), референси
відправника `ua_sender_ref`, `ua_sender_address_ref`, `ua_sender_contact_ref`, `np_api_url`
(типово `https://api.novaposhta.ua/v2.0/json/`). Поля та вкладка створюються коректно; проте валідації
чи тестового виклику API-ключа немає — ключ ніде не перевіряється проти сервера.

Flow DLV-2 — Дефолти сервісу та способу оплати. `[РЕАЛІЗОВАНО]` На картці перевізника задаються
`ua_default_service_type` (warehouse/doors/doors_warehouse/doors_doors — «склад-склад», «склад-двері» тощо),
`ua_default_payment_method` (sender/recipient/third_party) та прапорець `ua_cod_enabled` (накладений платіж).
Ці поля зберігаються і мають підставлятися у створення відправлення; наразі споживачів (методів, що їх
читають) немає, оскільки `*_send_shipping` є заглушкою.

Flow DLV-3 — Довідник відділень (структура). `[РЕАЛІЗОВАНО]` Модель `l10n_ua.delivery.warehouse` зберігає
відділення/поштомати: `name`, `carrier_type` (індексований), `warehouse_ref` (зовнішній ID),
`warehouse_number`, `warehouse_type` (warehouse/postomat/cargo), `city`+`city_ref`, `address`, `phone`,
`schedule`, `max_weight`, координати `latitude`/`longitude`. Обмеження `_unique_ref_carrier`
(`UNIQUE(warehouse_ref, carrier_type)`) гарантує унікальність референсу в межах перевізника. Доступ:
`stock.group_stock_user` — лише читання, `stock.group_stock_manager` — повний CRUD.

Flow DLV-4 — Пошук міста/відділення. `[ЧАСТКОВО]` У полях Many2one до `l10n_ua.delivery.warehouse` оператор
вводить текст → перевизначений `name_search` шукає за `name`, `warehouse_number` або `city` (OR-домен,
`ilike`). Пошук по локальному довіднику працює; але сам довідник наповнюється лише синхронізацією з API
(`np_sync_warehouses` тощо), яка є **заглушкою**, тож без ручного імпорту таблиця відділень порожня.

Flow DLV-5 — Синхронізація відділень Нова Пошта. `[ЗАГЛУШКА]` Менеджер натискає кнопку «Sync Warehouses»
(`np_sync_warehouses`, кнопка є у формі перевізника). Цільова поведінка: запит до методу `Address.getWarehouses`
API НП, upsert у `l10n_ua.delivery.warehouse` за `warehouse_ref`. Фактично метод містить `# TODO` і `pass` —
жодних записів не створюється. Для Meest (`meest_sync_warehouses`) та Укрпошти (`ukrposhta_sync_branches`)
кнопок у формах взагалі немає, методи також порожні.

Flow DLV-6 — Розрахунок вартості доставки (Нова Пошта). `[ЗАГЛУШКА]` Через кошик `sale.order` /
`delivery.carrier.rate_shipment()` викликається `np_rate_shipment(order)`. Цільова логіка: запит
`InternetDocument.getDocumentPrice` за вагою, оголошеною вартістю, містами відправника/одержувача та типом
сервісу. Фактично повертається `{'success': True, 'price': 0.0, ...}` — вартість завжди **0 грн**,
що не відповідає реальному тарифу. Аналогічно `ukrposhta_rate_shipment` та `meest_rate_shipment`.

Flow DLV-7 — Формування ТТН/експрес-накладної із замовлення. `[ЗАГЛУШКА]` Комірник підтверджує
`stock.picking` → ядро `delivery` викликає `send_shipping` → делегує `np_send_shipping(pickings)`. Цільова
логіка: `InternetDocument.save` (створення ТТН), запис номера у `picking.carrier_tracking_ref`, повернення
`exact_price`. Фактично повертається `[{'exact_price': 0.0, 'tracking_number': ''}]` — **номер ТТН не
генерується**. Реальна взаємодія з реєстром НП, друк дати відправлення тощо відсутні.

Flow DLV-8 — Друк маркування/наклейки. `[ЗАГЛУШКА]` Після створення ТТН комірник має отримати PDF-наклейку
(маркування 100×100 з номером ТТН, штрих-кодом, одержувачем, відділенням). У міксині для цього передбачено
`ua_print_label(picking)`, який наразі викидає `NotImplementedError()`. У модулях перевізників окремого
методу друку немає взагалі — функціонал не реалізовано.

Flow DLV-9 — Трекінг статусу посилки (посилання). `[РЕАЛІЗОВАНО]` Для відправлення з
`picking.carrier_tracking_ref` метод `np_get_tracking_link(picking)` повертає готовий URL
`https://novaposhta.ua/tracking/?cargo_number=<ref>`. Аналогічно `ukrposhta_get_tracking_link`
(`track.ukrposhta.ua/...?barcode=<ref>`) та `meest_get_tracking_link` (`meest.ua/tracking?number=<ref>`).
Це єдина реально працююча функція трекінгу.

Flow DLV-10 — Автоматичне оновлення статусу посилки. `[ЗАГЛУШКА]` Періодичне підтягування статусу («в дорозі»,
«прибула у відділення», «вручено», «повернення») мало б реалізовуватися через `ua_get_tracking(tracking_number)`
міксину (`TrackingDocument.getStatusDocuments` для НП). Метод викидає `NotImplementedError()`; крон-завдання
періодичного трекінгу немає. Статуси посилок у системі не оновлюються автоматично.

Flow DLV-11 — Накладений платіж (COD). `[ЗАГЛУШКА]` На перевізнику вмикається `ua_cod_enabled=True`,
`ua_default_payment_method` визначає, хто платить за доставку. Цільова логіка: при створенні ТТН передати суму
накладеного платежу (BackwardDeliveryData для НП), відстежити зворотне повернення коштів на рахунок
продавця та звірити з `sale.order`. Оскільки `*_send_shipping` — заглушка, COD фактично не передається;
поля для суми накладеного платежу та обліку його повернення в моделях **відсутні**.

Flow DLV-12 — Укрпошта: створення відправлення. `[ЗАГЛУШКА]` Перевізник з `ua_carrier_type='ukrposhta'` →
`ukrposhta_send_shipping` мав би формувати відправлення через Ukrposhta API (модель `Shipment`), працювати з
поштовими індексами (5 цифр) та адресною доставкою. Метод повертає порожній `tracking_number`. Специфіка
Укрпошти (індекси, розділення на адресну/до відділення, формат ШК) не реалізована; окремих полів індексу немає
(є загальне `warehouse_number` у довіднику).

Flow DLV-13 — Meest: створення відправлення. `[ЗАГЛУШКА]` Перевізник `ua_carrier_type='meest'` →
`meest_send_shipping`/`meest_rate_shipment`/`meest_sync_warehouses` — усі повертають заглушки або `pass`.
Інтеграція з Meest API не виконана; довідник відділень Meest не наповнюється.

Flow DLV-14 — Зворотна доставка / повернення посилки. `[ЗАГЛУШКА]` Для повернення товару споживачем цільова
логіка: створення зворотної ТТН (тип сервісу «doors_warehouse»/«warehouse_warehouse» у зворотному напрямку,
BackwardDelivery). Спеціального методу створення повернення немає; `np_cancel_shipment`/`ukrposhta_cancel_shipment`/
`meest_cancel_shipment` (скасування ТТН) містять лише `pass`. Обробка повернень і скасувань не працює.

Flow DLV-15 — Вибір типу сервісу «двері-двері» з кур'єром. `[ЧАСТКОВО]` Оператор обирає
`ua_default_service_type='doors_doors'` (адресна доставка від дверей до дверей). Поле коректно зберігається і
має транслюватися у параметр сервісу при створенні ТТН. Через заглушку `*_send_shipping` реального ефекту немає;
адреса одержувача (вулиця/будинок/квартира як окремі структуровані поля) у моделях доставки не деталізована —
використовується стандартний `res.partner`.

Flow DLV-16 — Мультиперевізникове замовлення (вибір найдешевшого). `[ЗАГЛУШКА]` Для одного `sale.order`
менеджер порівнює тарифи кількох `delivery.carrier` (НП/Укрпошта/Meest) через `rate_shipment`. Оскільки всі
`*_rate_shipment` повертають `price=0.0`, порівняння беззмістовне — усі перевізники «безкоштовні». Автовибір
найвигіднішого перевізника не реалізовано.

Flow DLV-17 — Габарити/вага та обмеження відділення. `[ЧАСТКОВО]` Довідник відділень має поле `max_weight`
(макс. вага, кг) і `warehouse_type` (зокрема `postomat` — поштомат з жорсткими обмеженнями габаритів). Дані
зберігаються, але жодна логіка не перевіряє вагу/габарити відправлення проти `max_weight` відділення-одержувача
перед створенням ТТН — валідація відсутня.

Flow DLV-18 — Прив'язка перевізника до правил доставки sale/stock. `[РЕАЛІЗОВАНО частково ядром]` Український
перевізник виступає звичайним `delivery.carrier`, тож стандартні механізми Odoo (додавання рядка доставки в
`sale.order`, генерація `stock.picking`, поле `carrier_id`) працюють з коробки. Українська специфіка (ТТН, COD,
відділення) поверх цього — незавершена (див. DLV-6…DLV-14).

## Звірка з законодавством

| Функція в системі | Норма права | Стан відповідності |
|---|---|---|
| Діяльність служб доставки як операторів поштового зв'язку | Закон України «Про поштовий зв'язок» від 04.10.2001 № 2759-III | Каркас під перевізників є; ТТН/накладна як документ поштового відправлення не формується (заглушка). |
| Правила надання послуг з доставки, договір, ТТН/накладна | Правила надання послуг поштового зв'язку, Постанова КМУ від 05.03.2009 № 270 | Реквізити відправника (`ua_sender_ref` тощо) та відділень є; сама накладна не генерується. Товарно-транспортна накладна — Наказ Мінтрансу № 363 (орієнтовно, для авто-перевезень). |
| Доставка при дистанційному (онлайн) продажу | Закон України «Про електронну комерцію» від 03.09.2015 № 675-VIII | Інтеграція з `sale`/`stock` передбачена, але створення відправлення й фіксація факту доставки не реалізовані. |
| Повернення товару споживачем, зворотна доставка | Закон України «Про захист прав споживачів» від 12.05.1991 № 1023-XII (нова ред. 2023 — Закон № 3153-IX, орієнтовно), ст. про повернення товару належної/неналежної якості | Зворотні ТТН і скасування не працюють (DLV-14) — юридично значущий процес повернення не покритий. |
| Накладений платіж (COD) і касова дисципліна | Положення про касові операції НБУ № 148; Закон про РРО № 265/95-ВР (розрахункові операції) | Прапорець `ua_cod_enabled` є, але сума накладеного платежу, її повернення продавцю та зв'язок з РРО/касою **не реалізовані** — ризик неврахованих готівкових розрахунків. |
| Персональні дані одержувача (ПІБ, телефон, адреса) | Закон України «Про захист персональних даних» № 2297-VI; GDPR (для транскордонних, орієнтовно) | Дані одержувача беруться зі стандартного `res.partner`; спеціальних заходів (згода на передачу перевізнику, мінімізація, журналювання) немає. Оскільки API-виклики відсутні, ПД поки не передаються назовні, але при реалізації це стане обов'язковим. |

### Ключові прогалини (flagged honestly)

1. **Реальних API-викликів немає.** Усі методи розрахунку, створення ТТН, синхронізації відділень і
   скасування — заглушки з `# TODO`. Домен непридатний до продуктивної експлуатації.
2. **Трекінг неповний.** Працює лише формування посилання (`*_get_tracking_link`); автоматичне оновлення
   статусів (`ua_get_tracking` → `NotImplementedError`) і крон відсутні.
3. **Накладений платіж не оброблюється.** Немає полів суми COD, обліку повернення коштів, зв'язку з касовою
   дисципліною/РРО — критично для дистанційної торгівлі.
4. **Друк маркування відсутній.** `ua_print_label` → `NotImplementedError`; PDF-наклейка не генерується.
5. **Довідник відділень порожній без ручного заповнення** — синхронізація з API не працює; отже пошук
   міста/відділення (DLV-4) технічно робочий, але без даних.
6. **Персональні дані одержувача** обробляються без спеціальних гарантій; при увімкненні реальних інтеграцій
   потрібні згода на передачу перевізнику та журналювання (ЗУ № 2297-VI).
