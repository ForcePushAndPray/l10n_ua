Тестові сценарії блоку «Ціни постачальників»

Домен автоматизує завантаження прайс-листів постачальників із зовнішніх джерел (локальний файл, HTTP API, SFTP) у різних форматах (CSV/XLSX/XML/JSON), зіставлення позицій прайсу з номенклатурою Odoo та оновлення закупівельних цін у `product.supplierinfo`, звідки ціни підставляються в замовлення на закупівлю. Реалізовано шістьма модулями: рушій `l10n_ua_supplier_prices_base` (моделі, state machine, JSON-парсер, ручний завантажувач) + підключувані парсери `_csv` / `_xlsx` / `_xml` та завантажувачі `_api` / `_sftp`. Архітектура розділяє два незалежні шари на джерелі (`l10n_ua.supplier.price.source`): `fetcher_type` (_звідки_ взяти файл: `manual` / `api` / `sftp`) і `parser_type` (_як_ розібрати: `json` / `csv` / `xml` / `xlsx`), які комбінуються довільно. Ролі: **менеджер із закупівель** (налаштування джерел, запуск і контроль імпортів, актуальність закупівельних цін) та **контент-менеджер** (маппінг колонок, обробка нових/невідомих позицій, наповнення номенклатури).

Flow SUP-1 — Налаштування джерела прайсу. Створення джерела `l10n_ua.supplier.price.source` (Закупівлі → Supplier Prices → Configuration → Sources): назва, постачальник (`partner_id` — контрагент, чиї ціни імпортуємо), компанія (`company_id` nullable = ціни глобальні для всіх компаній групи), валюта за замовчуванням (`currency_default_id`), політика `unknown_sku_action` (`skip` / `log_only` / `create_product` / `error_stop`). Задаються `fetcher_type` і `parser_type`, а для завантажувачів — JSON-поле `connection_config`. Дефолтні таймаути (`fetch_timeout` 60 с, `parse_timeout` 300 с, `apply_timeout` 600 с, `watchdog_timeout_minutes` 30) захищають воркер від зависання; модель успадковує `mail.thread`.

Flow SUP-2 — Маппінг колонок на поля Odoo. Створення маппінгу `l10n_ua.supplier.price.mapping` з `record_path` (шлях до масиву записів — для табличних CSV/XLSX не потрібен, для XML це XPath `//product`, для JSON dotted-шлях `items`) і `parser_config` (JSON з параметрами конкретного парсера). Рядки полів `.mapping.field` описують `target` (`sku`, `name`, `price`, `currency`, `qty_min`, `uom`, `date_valid`, `barcode`, `description`), `source_path`, `required`, `default_value`, `transform` + `transform_param`. Мінімально обов'язкові target — **sku** і **price**; маппінг прив'язується до джерела.

Flow SUP-3 — Трансформації значень при парсингу. Кожне поле маппінгу може мати `transform` із `tools/transforms.py`: `strip`, `upper`, `lower`, `replace_comma`, `to_float`, `to_decimal`, `parse_date` (формат у `transform_param`, напр. `%d.%m.%Y` для `"17.04.2026"`), `multiply` (множник у `transform_param`). Українська специфіка: `to_float` знімає десяткову кому (`"15,50"` → `15.50`), типову для прайсів, вивантажених із 1С. Помилка трансформації обов'язкового поля переводить рядок у статус `error`, не зупиняючи весь прогін.

Flow SUP-4 — Транспорт manual (локальний файл). `fetcher_type = manual` — базовий режим без зовнішніх систем: файл прайсу прикріплюється вручну прямо у прогін імпорту, `_do_fetch()` кладе його в `raw_file`. Ідеальний для разових прайсів і першого тесту — достатньо CSV/XLSX з диска, жодних мережевих доступів. Комбінується з будь-яким `parser_type`.

Flow SUP-5 — Транспорт-парсер CSV. Модуль `l10n_ua_supplier_prices_csv` додає `parser_type = 'csv'` і перевизначає `_do_parse()` → `_parse_csv()`. `parser_config`: `delimiter` (`;` для українських прайсів), `encoding` (`utf-8`/`utf-8-sig`/`windows-1251`/`cp1251` з fallback), `has_header`, `skip_rows`, `quotechar`. За `has_header=True` `source_path` — назва колонки (`Артикул`), за `False` — 0-based індекс (`2`). Реальний робочий парсер (10 тестів).

Flow SUP-6 — Транспорт-парсер XLSX. Модуль `l10n_ua_supplier_prices_xlsx` (Python-залежність `openpyxl`) додає `parser_type = 'xlsx'` → `_parse_xlsx()`. `parser_config`: `sheet_name` (ім'я/індекс, дефолт — перший лист), `header_row` (1-based), `has_header`, `skip_rows`. `source_path` — назва колонки, літера (`A`, `AC`) або індекс; datetime-комірки повертаються як date, числові ціни вже float (transform не потрібен). Реальний робочий парсер (13 тестів).

Flow SUP-7 — Транспорт-парсер XML. Модуль `l10n_ua_supplier_prices_xml` (Python-залежність `lxml`) додає `parser_type = 'xml'` → `_parse_xml()`. `record_path` — XPath до записів (`//product`), `source_path` — відносний XPath (`./code/text()`, `@sku`, `./price/@value`, `string(./name)`). `parser_config`: `namespaces` (мапа префіксів NS) та `encoding` (примусова заміна — 1С часто віддає cp1251 у declaration). Реальний робочий парсер (9 тестів).

Flow SUP-8 — Вбудований парсер JSON. Рушій `base` містить `_parse_json` + хелпер `tools/json_path.py` (вибірка за шляхом `items[*].price.value`, dotted + `[n]` + `[*]`) без зовнішньої залежності на `jsonpath-ng`. `record_path = items`, `source_path` — dotted-шлях у записі (`price.value`). Це базовий `parser_type = 'json'`, доступний одразу після встановлення рушія.

Flow SUP-9 — Транспорт-завантажувач HTTP API. Модуль `l10n_ua_supplier_prices_api` (Python-залежність `requests`) додає `fetcher_type = 'api'` → `_fetch_api()`. `connection_config`: `url`, `method` (GET/POST), `auth_type` (`none`/`basic`/`bearer`/`api_key_header`) з обліковими даними (`username`/`password`/`token`/`header_name`), `headers`, `params`, `body`, `response_type` (`file` — тіло і є файлом; `json_indirect` — відповідь містить посилання, за `json_indirect_path` робиться другий запит). Timeout з `source.fetch_timeout`. Реальний код, але 12 тестів ганяються з **мокнутим** `requests.Session` — без живого ендпоінта не верифікований (див. FLAG).

Flow SUP-10 — Транспорт-завантажувач SFTP. Модуль `l10n_ua_supplier_prices_sftp` (Python-залежність `paramiko`) додає `fetcher_type = 'sftp'` → `_fetch_sftp()`. `connection_config`: `host`, `port` (22), `username`, автентифікація `password` або `key_file` (+`key_passphrase`), `remote_path`, `host_key_policy` (`reject` дефолт / `auto_add` / `warning`). Реальний код, але 10 тестів із **мокнутим** `paramiko.SSHClient` — без реального SFTP-сервера не верифікований (див. FLAG).

Flow SUP-11 — State machine прогону імпорту. Прогін `l10n_ua.supplier.price.import` (номер за `ir.sequence` `SPI/YYYY/NNNNN`) проходить `draft → fetching → fetched → parsing → parsed → applying → done` (гілка `error`). Три кнопки шапки: **Fetch** (`action_fetch` → `_do_fetch()`, диспетчер за `fetcher_type`), **Parse** (`action_parse` → `_do_parse()`, диспетчер за `parser_type`, розбирає `raw_file` у рядки `import.line`), **Apply** (`action_apply` → `_do_apply()`, оновлює `supplierinfo`). Переходи валідуються тільки через `_set_state()`; action-методи **не викидають UserError** (raise робить rollback і губить `state='error'`) — за помилки пишуть `error_log` + `message_post`, кнопка **Restart** (`action_restart`) повертає в `draft`. `raw_file` зберігається в `ir.attachment`, тож парсинг повторюється без повторного завантаження.

Flow SUP-12 — Зіставлення товару. `import.line._find_product()` шукає `product.product` виключно за парою _постачальник + `product_code`_: домен `[('partner_id','=',partner.id),('product_code','=',supplier_sku)]` по `product.supplierinfo`, `limit=1`, повертає `product_id` або варіант шаблону. Зіставлення відбувається **лише за артикулом (SKU)** — поля `barcode`/`supplier_name` на рядку зберігаються, але в пошуку не беруть участі, порогу схожості немає (див. FLAG). Знайдений рядок отримує статус `matched`.

Flow SUP-13 — Обробка невідомих (нових) позицій. Якщо `_find_product()` нічого не знайшов, `_handle_unknown_sku()` діє за політикою джерела `unknown_sku_action`: `skip` (статус `skipped`), `log_only` (статус `unknown` — залишити для ручного розбору контент-менеджером), `error_stop` (raise → весь прогін у `error`), `create_product` (створити `product.product` з `default_code = supplier_sku`, `name`, `barcode`, `type='consu'`, `purchase_ok=True`; статус `created`). Це ключовий важіль контролю: за замовчуванням безпечний `skip`, `create_product` — для довірених повних прайсів.

Flow SUP-14 — Оновлення product.supplierinfo. `_apply_to_supplierinfo()` для кожного розпізнаного рядка робить find-or-create запису постачальника: домен пошуку _партнер + `product_code`_ (+ `company_id` або `False` для глобальних). Записуються `price`, `currency_id` (валюта рядка або `currency_default_id` джерела), `min_qty` (`qty_min`), `product_name`, `date_start` (з `date_valid`). Наявний запис оновлюється (`write`), новий — створюється з прив'язкою `product_id`/`product_tmpl_id`. Саме ці ціни далі підставляються в замовлення на закупівлю.

Flow SUP-15 — Cron автозавантаження за розкладом. На джерелі вмикається `auto_sync_active` + `sync_interval_hours` (напр. 24). Крон `_cron_auto_sync()` шукає активні джерела з `auto_sync_active=True` і створює нові `draft`-імпорти, коли з останнього прогону минув інтервал. Прайс постачальника оновлюється без участі оператора (fetch→parse→apply автоматично). Constraint `_check_sync_interval` забороняє інтервал < 1 год при увімкненій авто-синхронізації.

Flow SUP-16 — Watchdog і стратегія таймаутів. Чотири рівні таймаутів на джерелі: `fetch_timeout` (мережеві API/SFTP), `parse_timeout` (deadline-check на кожному записі), `apply_timeout` (deadline на кожному чанку), `watchdog_timeout_minutes`. Apply обробляє рядки батчами по 500 з `env.cr.commit()` після кожного чанку — звільняє row-locks на `product.supplierinfo`, оновлює `write_date`, обмежує пам'ять на прайсах 50k+ рядків. Крон `_cron_watchdog()` (кожні 5 хв) переводить «застряглі» імпорти в станах `fetching/parsing/applying` у `error`, якщо `write_date` старіший за `watchdog_timeout_minutes` — зависла мережа не блокує воркер, реран безпечний через find-or-create.

Flow SUP-17 — Історія та лог імпорту. Шапка прогону веде лічильники `line_count` / `matched_count` / `unknown_count` / `error_count` + `error_log`; кожен `import.line` має власний `status` (`pending`/`matched`/`unknown`/`created`/`skipped`/`error`) та `error_message` для аудиту (видно, чому рядок пропущено чи який товар створено). Стани й причини помилок дублюються в statusbar і чатер (`mail.thread`). Прогони не видаляються — накопичується історія завантажень для контролю змін закупівельних цін у часі.

Flow SUP-18 — Націнка / переоцінка (обмежено). Повноцінного рушія правил націнки/переоцінки в домені **немає**: `price` записується в `supplierinfo` як є, у валюті рядка/джерела. Єдиний доступний важіль коригування — column-level transform `multiply` (`transform_param` = коефіцієнт), який множить ціну прайсу на фіксований множник (напр. груповий курсовий коефіцієнт чи технічна поправка). Це не бізнес-правила націнки з умовами по групах/брендах/обсягах — див. FLAG; фінальна продажна націнка лишається за межами домену (стандартний прайсинг Odoo поверх закупівельної ціни).

## Звірка з законодавством

**Важлива примітка:** цей домен — переважно **технічна інтеграція** (ETL прайс-листів), а не предметна ділянка з прямим галузевим регулюванням. Пряме нормативне навантаження мінімальне; нижче — дотичні норми, а не вимоги, які модуль реалізує «по букві».

- **Закупівельна ціна як елемент собівартості** — Закон України «Про бухгалтерський облік та фінансову звітність в Україні» (№ 996-XIV) та НП(С)БО 9 «Запаси»: ціна з `product.supplierinfo`, яку оновлює домен, формує первісну вартість запасів при оприбуткуванні. Модуль лише постачає актуальну закупівельну ціну; власне визнання собівартості — в обліковому контурі (орієнтовно).
- **Договірне ціноутворення** — ст. 632 ЦКУ (ціна за домовленістю сторін) та ст. 189–198 ГКУ: прайс постачальника є комерційною пропозицією/додатком до договору поставки; система фіксує узгоджену договірну ціну, не встановлюючи регульованих цін.
- **Електронний обмін даними** — Закон України «Про електронну комерцію» (№ 675-VIII) та Закон «Про електронні документи та електронний документообіг» (№ 851-IV): транспорти API/SFTP реалізують електронний обмін комерційною інформацією між сторонами (орієнтовно — прямих вимог до формату прайсу закон не ставить).
- **Захист комерційної таємниці та персональних даних** — ст. 505–508 ЦКУ (комерційна таємниця) і Закон «Про захист персональних даних» (№ 2297-VI): прайси й облікові дані доступу є конфіденційними; звідси вимога обмеження прав доступу (`ir.model.access`) і безпечного зберігання секретів (нижче — FLAG).

### FLAG — чесна оцінка повноти й ризиків

- **Транспорти: реальні vs заглушки.** Усі 6 модулів мають реалізований код і робочі юніт-тести (base 44, csv 10, xlsx 13, xml 9, api 12, sftp 10). CSV/XLSX/XML-парсери та manual-завантажувач проганяються **без зовнішніх систем** і фактично верифіковані. **API та SFTP — реальний код, але тести використовують моки** (`requests.Session`, `paramiko.SSHClient`); проти живого ендпоінта постачальника вони не прогнані, тож на першому продакшн-підключенні можливі несподіванки (кодування, ланцюжки редіректів, host-key, нестандартні відповіді). Це не заглушки-`pass`, але й не польова інтеграція.
- **Безпека зберігання облікових даних.** Реквізити API/SFTP (`token`, `password`, `key_file`, `key_passphrase`) зберігаються в полі `connection_config` **відкритим текстом** у БД. Для production це прямий ризик щодо захисту комерційної таємниці/ПДн — облікові дані слід винести в `ir.config_parameter` або зашифроване сховище секретів (наразі TODO).
- **Повнота зіставлення товарів.** Зіставлення працює **виключно за артикулом (SKU → `product_code`)**. Поля `barcode` і `supplier_name` на рядку зберігаються, але в пошуку **не використовуються**; зіставлення за штрихкодом, за назвою та порогу схожості (fuzzy match) **немає** — усупереч типовому очікуванню. Для прайсів без стабільних артикулів або з розбіжними кодами частина позицій потраплятиме в `unknown` і вимагатиме ручного розбору контент-менеджером.
- **Націнка/переоцінка.** Окремого рушія правил націнки немає — лише column-level transform `multiply` як фіксований коефіцієнт (див. Flow SUP-18). Умовні правила переоцінки (по групах товарів, брендах, обсягах, курсі валют на дату прайсу) не реалізовані.
- **Конвертація валют.** Заявлено конвертацію по курсу через `product.supplierinfo.currency_id`, але історії курсів НБУ на дату прайсу (`date_valid`) у домені немає — валюта переноситься по-рядково, перерахунок покладається на стандартний механізм Odoo (орієнтовно).
