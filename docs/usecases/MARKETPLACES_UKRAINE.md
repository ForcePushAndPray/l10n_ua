Тестові сценарії блоку «Маркетплейси»

Домен покриває інтеграцію Odoo 19 з українськими торговими майданчиками та прайс-агрегаторами: імпорт замовлень (Rozetka, Prom.ua), двосторонню синхронізацію статусів, вивантаження товарів/залишків/цін через API та генерацію YML-фідів (Hotline, Price.ua). Ядро — модуль `l10n_ua_marketplace_base` (моделі `marketplace.backend`, `marketplace.order`, `marketplace.pricelist`/`marketplace.pricelist.item`, `marketplace.category`, `marketplace.status.mapping`, `marketplace.payment.status`), який розширюють `l10n_ua_marketplace_rozetka`, `l10n_ua_marketplace_prom`, `l10n_ua_marketplace_hotline`, `l10n_ua_marketplace_priceua`. Ролі: **менеджер маркетплейсу** (налаштування backend, токени, статуси), **контент-менеджер** (прайс-листи, категорії, фіди), **оператор замовлень** (обробка `marketplace.order`, відвантаження, скасування, оплата).

Стан backend: `draft → active → error` (плюс архівний прапорець `active`; окремого стану `inactive` немає — деактивація виконується зняттям `active`). Стан замовлення: `new → confirmed → processing → shipped → delivered`, з відгалуженнями `cancelled` та `returned`. Крони: імпорт замовлень — кожні 15 хв (`_cron_import_orders_all`), синхронізація залишків — 30 хв (`_cron_sync_stock_all`), цін — 1 год (`_cron_sync_prices_all`), оновлення токенів — 12 год (`_cron_refresh_tokens`).

Flow MP-1 — Налаштування backend Rozetka. Створення `marketplace.backend` з `marketplace_type='rozetka'` → введення `rozetka_username`/`rozetka_password` (поля під `groups='base.group_system'`) → `action_test_connection` викликає `_api_authenticate`: POST на `https://api-seller.rozetka.com.ua/sites`, у відповіді `content.access_token` записується в `api_token`, `api_token_expiry` = зараз + 23 год → `action_activate` переводить backend у `state='active'`. Автоматично генерується `code` через `ir.sequence` (`marketplace.backend`).

Flow MP-2 — Налаштування backend Prom.ua. Backend з `marketplace_type='prom'` → `api_url` за замовчуванням `https://my.prom.ua/api/v1` (через `_onchange_marketplace_type_prom`) → `api_key` — статичний Bearer-токен без оновлення → `action_test_connection` робить GET `/cabinet/company`, зберігає `prom_company_id` і викликає `_clear_error`. `_api_authenticate` для Prom лише повертає `api_key` (жодного OAuth-потоку).

Flow MP-3 — Автооновлення токена Rozetka. Крон `_cron_refresh_tokens` (кожні 12 год) вибирає активні backend з `api_token_expiry <= now + 2 год` → викликає `action_refresh_token` → повторний `_api_authenticate`. Додатково при будь-якому запиті `_get_rozetka_headers` перевіряє прострочення токена, а `_rozetka_api_request` на відповідь HTTP 401 автоматично реавтентифікується і повторює виклик. Prom-токен статичний, тож `action_refresh_token` для нього повертає `True` без дій.

Flow MP-4 — Імпорт замовлень Rozetka з пагінацією. `_import_orders` бере `from_date = import_orders_last or import_orders_from_date` → `_api_get_orders` циклічно тягне `GET /orders` з `per-page=100`, `expand=items,delivery,payment`, збільшуючи `page` до досягнення `_meta.pageCount` → для кожного замовлення перевірка дубля за (`backend_id`, `external_id`), нові створюються через `_prepare_rozetka_order_vals` + `_create_lines_from_rozetka`. Числові коди статусу Rozetka (1–7) мапляться в internal state (`1→new … 5→delivered, 6→cancelled, 7→returned`). Наприкінці оновлюється `import_orders_last`.

Flow MP-5 — Імпорт замовлень Prom.ua з пагінацією. `_api_get_orders` викликає `GET /orders/list` з `limit=100` та зростаючим `offset`, доки повертається повна сторінка → `_prepare_prom_order_vals` мапить текстові статуси (`pending→new`, `received→confirmed`, `paid→processing`, `delivered→delivered`, `canceled→cancelled`), парсить ISO-дату `date_created`, витягує клієнта/доставку/ТТН із вкладених структур. Рядки створюються `_create_lines_from_prom`; повний JSON зберігається у `raw_data`.

Flow MP-6 — Мапінг статусів (двосторонній). `action_sync_statuses` наповнює `marketplace.status.mapping` типовими кодами майданчика (Rozetka — числові 1–7, Prom — текстові) з прапорцями `sync_from_marketplace`/`sync_to_marketplace`. При імпорті `_get_odoo_state(code)` повертає internal state за активним маппінгом (fallback `new`); при зміні в Odoo `_get_marketplace_code(state)` дає зовнішній код для відправки. Обмеження `UNIQUE(backend_id, external_code)` не допускає дублів кодів у межах backend.

Flow MP-7 — Створення sale.order із замовлення. `action_create_sale_order` (або автоматично при `auto_create_sale_order`) → `_find_or_create_partner` за режимом backend (`always`/`if_not_found`/`never`) шукає партнера за телефоном/email (`partner_search_by`, з нормалізацією номера до 10 цифр) або створює нового → `_prepare_sale_order_vals` заповнює `client_order_ref`, склад, команду продажів → рядки переносяться через `_prepare_sale_order_line_vals` з пошуком товару за `default_code`/`barcode`. За `auto_confirm_sale_order` замовлення одразу підтверджується.

Flow MP-8 — Життєвий цикл замовлення. `action_confirm` (state=`confirmed`, `confirm_date`), `action_ship`/`action_mark_shipped` (state=`shipped`, `tracking_number` ТТН), `action_deliver` (state=`delivered`) → кожна дія намагається виконати `_api_update_order_status`, який пушить відповідний код на майданчик (Rozetka PUT `/orders/{id}`, Prom POST `/orders/{id}/set_status`). Якщо для типу майданчика метод не реалізовано (`NotImplementedError`) — статус змінюється лише локально.

Flow MP-9 — Скасування замовлення. `action_cancel` відкриває `marketplace.order.cancel.wizard` зі списком причин, що доповнюється специфічними для майданчика (`ROZETKA_CANCEL_REASONS`, `PROM_CANCEL_REASONS`) → `action_cancel_direct` ставить state=`cancelled`, викликає `_api_cancel_order` (Rozetka — статус 6, Prom — `canceled` з мапінгом причини) → скасовує пов'язаний `sale.order` (`_action_cancel`) і пише запис у chatter. Помилка синхронізації з майданчиком логується, але локальне скасування зберігається.

Flow MP-10 — Повернення товару. Майданчик повертає код повернення (Rozetka `7`, окремий статус) → при імпорті/оновленні (`_update_from_rozetka`/`_update_from_prom`) state переходить у `returned`. Спеціальної обробки зворотної логістики чи компенсацій у моделі немає — це лише термінальний стан замовлення (обмеження функціоналу, орієнтовно).

Flow MP-11 — Реєстрація оплати. За наявності `payment_journal_id` та `is_paid` від майданчика `_register_payment` підтверджує `sale.order`, створює й проводить рахунок (`_create_invoices` → `action_post`), потім через майстер `account.payment.register` реєструє `account.payment` і проставляє `payment_id`, `payment_date`, `payment_amount`, `is_paid=True`. Доступний і ручний виклик `action_register_payment`; `auto_register_payment` дозволяє автоматизацію.

Flow MP-12 — Формування прайс-листа для вивантаження. `marketplace.pricelist` прив'язується до backend і (опційно) до Odoo `product.pricelist` → `action_generate_items` за доменом (`sale_ok`, категорії `category_ids`, кастомний `product_domain`, фільтр наявності зображення) створює `marketplace.pricelist.item` → `_compute_price` рахує ціну: база з прайс-листа/`lst_price`, націнка `price_margin`, округлення `price_round`, поріг `min_price`, перевизначення `price_promo`. `action_publish` переводить позиції у `pending`/`published`.

Flow MP-13 — Синхронізація залишків (батч). Крон `_cron_sync_stock_all` (30 хв) або `action_sync_stock_now` → `_sync_stock` вибирає позиції у стані `published`/`pending` з непорожнім `external_id` → розбиває на пакети `sync_batch_size` (типово 100) і викликає `_api_sync_stock_batch`. Rozetka шле PUT `/items/stock` списком `{id, stock}`, Prom — POST `/products/edit` (або `/products/{id}/edit`). Режим `sync_error_handling` (`continue`/`retry`/`stop`) визначає реакцію на збій; помилки записуються у `sync_error` позиції.

Flow MP-14 — Синхронізація цін. Крон `_cron_sync_prices_all` (1 год) або `action_sync_prices_now` → `_sync_prices`/`_api_sync_prices_batch`: Rozetka PUT `/items/prices` (`{id, price, old_price}`), Prom POST `/products/edit` з `price` та `discount` (тип `amount`), якщо `price_original > price`. Пакетна обробка, `last_sync` і `sync_error` оновлюються поштучно; при `retry` — фолбек на індивідуальні виклики.

Flow MP-15 — Генерація YML-фіда. Публічний ендпоінт `/marketplace/feed/<backend_id>` (`type='http'`, `auth='public'`) → `_generate_feed` → `_generate_yml_feed` будує `yml_catalog/shop` з валютою, деревом категорій (`<categories>` з `external_id`/`parentId`) та `<offers>` для позицій у стані `published` (id, `vendorCode`, url, `price`/`oldprice`, `categoryId`, `picture`, `name`, характеристики як `<param>`). Позиції поза наявністю відсікаються за `include_out_of_stock`/`min_qty_available`; при `feed_auth_enabled` вхід захищено Basic Auth (`feed_auth_login`/`feed_auth_password`). Формат `csv` присутній у виборі, але не реалізований, а `xml` наразі дублює YML (обмеження).

Flow MP-16 — Категорії маркетплейсу (мапінг external ID). `marketplace.category` — ієрархічна модель (`_parent_store`, `full_path`) з `external_id`, унікальним у межах `marketplace_type` → `get_or_create(type, external_id, name, parent_external_id)` знаходить або створює вузол із прив'язкою до батька → `odoo_category_ids` (M2M) зіставляє категорію майданчика з `product.category` Odoo. Категорії підтягуються у YML-фід і в поле `marketplace_category_id` позиції прайс-листа.

Flow MP-17 — Прийом webhook. Ендпоінт `/marketplace/webhook/<backend_id>` (`type='jsonrpc'`, `auth='public'`, `csrf=False`) → за наявності `webhook_secret` перевіряється підпис HMAC-SHA256 (`X-Webhook-Signature`/`X-Signature`) → базовий контролер `_process_webhook` за типом події викликає `_process_new_order` (тригерить повний `_import_orders`) або `_process_order_update` (оновлює `marketplace_state`). УВАГА: моделі Rozetka/Prom мають власні `_process_webhook`/`_import_single_order`, але базовий контролер їх не викликає — обробка йде через контролерний метод, тож точкове створення замовлення з тіла webhook фактично не задіяне (потенційний дефект, орієнтовно). Також використовується `request.jsonrequest`, що в Odoo 19 застаріле.

Flow MP-18 — Прайс-агрегатори Hotline та Price.ua. Backend типів `hotline`/`priceua` працюють **лише через YML-фід** — API замовлень/залишків відсутній за задумом. Заповнюється довідковий `*_merchant_id` і (опційно) коренева категорія фіда → `action_copy_feed_url`/`_get_*_feed_url` віддають публічний URL `/marketplace/feed/<id>`, який реєструється в кабінеті агрегатора. Синхронізація односпрямована: майданчик періодично сам стягує фід.

Flow MP-19 — Клієнт із маркетплейсу (res.partner). При створенні партнера з замовлення проставляються `is_marketplace_customer=True`, `marketplace_source` (тип майданчика) і адреса доставки → `marketplace_order_ids`/`marketplace_order_count` та `action_view_marketplace_orders` дають зведення замовлень клієнта. Пошук існуючого партнера — за нормалізованим телефоном або email залежно від `partner_search_by`.

Flow MP-20 — Імпорт наявного каталогу з Prom.ua. `action_import_products` (лише для `prom`) циклічно тягне `GET /products/list` (limit/offset) → створює/доповнює `marketplace.pricelist` та `marketplace.pricelist.item` з `external_id`, `sku`, ціною, залишком і станом (`published`/`draft` за `presence`), намагаючись зіставити з Odoo-товаром за `default_code`. Це дозволяє зв'язати вже опубліковані на Prom позиції з номенклатурою Odoo для подальшої синхронізації.

## Звірка з законодавством

**Закон «Про електронну комерцію» № 675-VIII.** Замовлення з майданчика формує електронний правочин; система фіксує реквізити покупця, склад замовлення, суму, спосіб оплати/доставки (`marketplace.order` + `raw_data`) і породжує `sale.order`. Прогалина: немає окремого обліку публічної оферти/згоди покупця та обов'язкових відомостей про продавця в розрізі кожного замовлення — комерційна інформація зберігається на рівні `res.company`/каталогу, не фіксується як зміст правочину.

**Закон «Про захист прав споживачів» (дистанційна торгівля, повернення 14 днів).** Модель має стани `cancelled`/`returned` і довідник причин скасування, тобто відображає факт повернення. Прогалина: **немає** логіки 14-денного строку повернення, розрахунку/повернення коштів, обробки заяв споживача — стан `returned` суто інформаційний (Flow MP-10). Право на відмову й строки відстежуються вручну.

**Закон «Про захист персональних даних» № 2297-VI.** Персональні дані покупців (ПІБ, телефон, email, адреса) імпортуються у `res.partner` та повністю дублюються у `marketplace.order.raw_data` (сирий JSON відповіді API). Прогалини, які слід чесно позначити: відсутні згода на обробку, строк зберігання/знеособлення, журнал доступу; `raw_data` містить надлишкові ПД без очищення. Це зона підвищеного ризику для відповідності № 2297-VI.

**ПДВ і фіскалізація онлайн-продажу (ПРРО, Закон № 265/95-ВР про РРО).** Зв'язок із ПРРО **закритий/відсутній**: при оплаті створюється лише `account.payment` та рахунок (Flow MP-11), фіскальний чек через ПРРО не формується й не передається до ДПС. Для роздрібного онлайн-продажу з 2022 р. фіскалізація обов'язкова — це критична незакрита прогалина домену, яку потрібно реалізувати окремо (інтеграція з ПРРО/checkbox-подібним сервісом).

**Правила самих майданчиків (Rozetka Seller API, Prom.ua API).** Реалізовано реальні HTTP-виклики через `requests`: Rozetka — авторизація за логіном/паролем із Bearer-токеном на 24 год і реавтентифікацією на 401; Prom — статичний Bearer-токен. Hotline/Price.ua — виключно YML-фід згідно з їхніми вимогами до вивантаження. Це відповідає документованим API майданчиків.

### Чесні прапорці щодо реалізації

- **Скріншоти/демо-прохід.** Довідник домену (`docs/marketplaces.md`) і покроковий гайд (`docs/howto/marketplaces.md`) наявні, проте наживо на демо не пройдені: реальних скріншотів немає (потрібні API-ключі майданчиків), у HOWTO — текстові плейсхолдери. Демо-дані є (`demo/marketplace_demo.xml`).
- **Реальні API-виклики vs заглушки.** Rozetka та Prom роблять справжні мережеві запити. У базовій моделі `marketplace.backend` методи `_import_orders`, `_api_get_orders`, `_api_*` — заглушки (`NotImplementedError`/`return 0`); Hotline і Price.ua свідомо не мають API замовлень/залишків (тільки фід).
- **Зберігання токенів.** `api_key`/`api_secret`/`api_token`/`webhook_secret` — звичайні `Char`-поля під `groups='base.group_system'` (обмежене читання), але **без шифрування** в БД; твердження про «encrypted» у документації проекту не відповідає коду.
- **Webhook.** Модельні `_process_webhook` (Rozetka/Prom) не під'єднані до контролера; контролер використовує застаріле `request.jsonrequest` (Odoo 19). Точкове створення/оновлення замовлення з тіла webhook фактично підмінене повним імпортом — потребує перевірки (орієнтовно дефект).
- **Фіскалізація.** Інтеграції з ПРРО/ДПС немає взагалі — див. розділ вище.
- **Обробка персональних даних.** `raw_data` зберігає повний JSON із ПД без анонімізації; політики ретеншену немає.
