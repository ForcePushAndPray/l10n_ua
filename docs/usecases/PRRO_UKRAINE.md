# Тестові сценарії домену ПРРО

Домен реалізує **фіскалізацію розрахункових операцій** через програмні РРО (ПРРО)
для України: базові постачальник-незалежні моделі каси/зміни/чека
(`l10n_ua_prro_base`) та інтеграцію з хмарним сервісом **Checkbox**
(`l10n_ua_prro_checkbox`). Ключові моделі: `l10n_ua.prro.config` (каса ПРРО),
`l10n_ua.prro.checkbox.config` (підключення провайдера), `l10n_ua.prro.shift`
(робоча зміна, X/Z-звіти), `l10n_ua.prro.receipt` + `l10n_ua.prro.receipt.line`
(фіскальний чек і його рядки). Абстрактний `l10n_ua.prro.mixin` описує інтерфейс
дій (`action_open_shift`, `action_close_shift`, `action_x_report`,
`action_register_receipt`, `action_service_input`, `action_service_output`),
який фактично реалізує провайдер.

**Ролі:** касир (відкриває/закриває зміну, пробиває чеки — `cashier_id` на зміні),
старший касир (налаштування каси, службові операції, звірка), бухгалтер (звірка
підсумків, облік виручки, звітність). **Обов'язки за законом:** видача
фіскального чека на кожну розрахункову операцію, формування Z-звіту при закритті
зміни, передавання даних до ДПС (через ПРРО/сервіс Checkbox) — Закон
№265/95-ВР, наказ Мінфіну №13 від 21.01.2016.

> **ВАЖЛИВЕ ЗАСТЕРЕЖЕННЯ.** Модулі реалізують **клієнт** до API Checkbox
> (`https://api.checkbox.in.ua/api/v1/`), але **самі нічого не фіскалізують**.
> Реальна фіскалізація потребує діючого акаунта Checkbox, каси ПРРО,
> зареєстрованої в ДПС, і касира з ключем/логіном. На демо-сервері цих реквізитів
> немає — усі дії Флоу 2 повертають помилку автентифікації (стан → `error`).
> Живих числових прикладів із фіскального чека в howto свідомо немає; скріншоти
> до теки `img/prro/` ще **не додані**.

---

Flow PRRO-1 — Реєстрація каси ПРРО. **ПРРО → Configurations → Новий** створює
запис `l10n_ua.prro.config`: `name`, `provider` (`checkbox` / `vchasno` / `other`),
`fiscal_number` (фіскальний номер ПРРО з реєстрації в ДПС), `company_id`,
зв'язок із точками продажу `pos_config_ids` (Many2many до `pos.config`). Одразу
після збереження `state = not_configured` (касу створено, провайдер ще не
підключено), обчислюване `current_shift_id` порожнє. Каса — постачальник-незалежна:
логіка виконання винесена в mixin і реалізується окремим модулем провайдера
(Закон №265/95-ВР, ст. 2 — визначення ПРРО).

Flow PRRO-2 — Підключення провайдера Checkbox. **ПРРО → Checkbox → Новий**
створює `l10n_ua.prro.checkbox.config` (з чатером `mail.thread`): `name`,
`prro_config_id` (каса з Flow PRRO-1), `license_key` (ліцензійний ключ каси),
`auth_type` (`login` / `pin`) та відповідні реквізити (логін+пароль **або** PIN).
Стан `draft → configured → authenticated / error`. При зміні `auth_type` метод
`_clean_auth_fields` очищує неактуальні поля (перехід на PIN стирає логін/пароль,
і навпаки), щоб не залишати «мертвих» креденшелів.

Flow PRRO-3 — Перевірка зв'язку з ДПС. Кнопка **Test Connection**
(`action_test_connection`) викликає `CheckboxAPI.ping_tax_service()` →
`POST /cash-registers/ping-tax-service`. Це **єдина** дія, що працює **без**
токена касира (не потребує автентифікації) — перевіряє доступність фіскального
сервера ДПС. Успіх → сповіщення `display_notification`; помилка → стан `error`
і текст у `error_message`.

Flow PRRO-4 — Автентифікація касира. Кнопка **Authenticate**
(`action_authenticate`): для `login` — `POST /cashier/signin`, для `pin` —
`POST /cashier/signinPinCode` (з ліцензійним ключем). У відповіді `access_token`
зберігається, `token_expiry` = поточний час + 1 тиждень, `state = authenticated`.
Далі підтягуються дані касира (`cashier/me` → `cashier_id`, `cashier_name`) і каси
(`cash-registers/info` → `cash_register_id`, `cash_register_fiscal_number`,
`cash_register_name`), у чатер — запис про вхід. Кнопка **Sign Out**
(`action_signout`, `POST /cashier/signout`) обнуляє токен і повертає стан
`configured`/`draft`. Вхід касира під власним обліковим записом — вимога до
персоналізації РРО-операцій (Закон №265/95-ВР, ст. 3).

Flow PRRO-5 — Синхронізація ставок податків. Кнопка **Sync Taxes**
(`action_sync_taxes`, `GET /tax`) підтягує актуальні ставки податків із Checkbox
(`get_taxes()`) для коректного розрахунку ПДВ/акцизу в рядках чека. Наразі метод
лише повертає перелік і пише в чатер «Synced N tax rates» — **автоматичного
мапування отриманих ставок на податки Odoo (`account.tax`) ще немає** (орієнтовно
план). Виконувати до відкриття зміни.

Flow PRRO-6 — Відкриття робочої зміни. Кнопка **Open Shift**
(`action_open_shift`): спершу `api.get_shift()` (`GET /cashier/shift`) перевіряє,
чи немає вже відкритої зміни — якщо є, помилка «Shift is already open». Потім
`POST /shifts` відкриває зміну на боці Checkbox/ДПС, і в Odoo створюється запис
`l10n_ua.prro.shift`: `state = open`, `shift_number` = `serial` із відповіді,
`open_date` розібрано через `parse_checkbox_datetime(opened_at)`, `cashier_id` =
поточний користувач. Відкриту зміну видно як `current_shift_id` каси. Одна зміна
не може перевищувати 24 год (вимога порядку ведення РРО-операцій).

Flow PRRO-7 — Фіскальний чек продажу (позиції, ПДВ). Метод
`action_register_receipt(receipt_data)` викликає `POST /receipts/sell`. У Odoo
створюється `l10n_ua.prro.receipt` типу `sale`, `state = registered`, прив'язаний
до `current_shift_id`; із відповіді беруться `fiscal_number` (`fiscal_code`),
`local_number` (`serial`), `total_amount` (`total_sum` копійки ÷ 100). Рядок чека
`l10n_ua.prro.receipt.line` містить `name`, `uktzed_code` (код УКТЗЕД для
підакцизних/маркованих товарів), `quantity`, `price_unit`, `discount`, `tax_rate`
та обчислюваний `subtotal = quantity × price_unit × (1 − discount/100)`. Обов'язкові
реквізити чека — найменування, кількість, ціна, ставка та сума ПДВ (наказ Мінфіну
№13 від 21.01.2016). **Обмеження (чесно):** метод створює лише «шапку» чека —
рядки з `pos.order` **не переносяться автоматично**, `total_amount` пишеться прямо
з відповіді, а `line_ids` лишаються порожніми (відомий пункт планів).

Flow PRRO-8 — Форми оплати (готівка / картка / змішана). На чеку `payment_type`
= `cash` / `card` / `mixed`, суми — `cash_amount` і `card_amount`; обчислюване
`total_amount = cash_amount + card_amount`. Підсумки зміни розкладаються за формою
оплати: `total_cash` (чеки з `payment_type = cash`), `total_card` (`card`). Це
дозволяє звірити готівкову виручку в касі з Z-звітом. Змішана оплата (частина
готівкою, частина карткою) підтримується структурою полів, але передавання
`payment`-масиву в Checkbox формує викликова сторона в `receipt_data`.

Flow PRRO-9 — Чек повернення. Тип чека `return` зменшує підсумок `total_returns`
зміни (окремо від `total_sales`). У `CheckboxAPI` є `create_return_receipt()`
(`POST /receipts/return`), **але окрема кнопка-дія повернення з боку моделі ще не
задіяна** — тип `return` наразі виставляється вручну на записі
`l10n_ua.prro.receipt`, повноцінне фіскальне повернення потребує реального
підключення до ДПС. Повернення оформлюється окремим фіскальним чеком із
посиланням на первинний (вимога порядку ведення РРО-операцій).

Flow PRRO-10 — Службове внесення готівки. Кнопка/метод `action_service_input(amount)`
формує `receipt_data` з `payment.type = CASH`, `value = int(amount × 100)`
(додатна сума в копійках) і викликає `create_service_receipt()`
(`POST /receipts/service`). У чатер — «Service input: N UAH». Службове внесення
фіксує внесення розмінної готівки на початку зміни й впливає на залишок готівки в
касі (поле зміни `service_input`).

Flow PRRO-11 — Службова видача готівки. `action_service_output(amount)` —
аналогічно, але `value = −int(amount × 100)` (**від'ємна** сума), той самий
ендпоінт `/receipts/service`. Використовується для інкасації/вилучення готівки під
час зміни (поле зміни `service_output`). Внесення й видача не є продажем і не
збільшують оборот за Z-звітом.

Flow PRRO-12 — X-звіт (проміжний, без закриття зміни). Кнопка **X-Report**
(`action_x_report`, `POST /reports` через `create_x_report()`) формує проміжний
звіт про поточний стан зміни; у чатер — «X-Report generated». **Стан зміни НЕ
змінюється**, кнопку можна викликати багаторазово. Підсумки на записі зміни
(`receipt_count`, `total_sales`, `total_returns`, `total_cash`, `total_card`)
рахуються **автоматично** з прив'язаних чеків через `_compute_totals`. X-звіт —
контрольний інструмент касира/старшого касира протягом зміни.

Flow PRRO-13 — Z-звіт (закриття зміни). Кнопка **Close Shift (Z-Report)**
(`action_close_shift`, `POST /shifts/close`): із відповіді береться `z_report.serial`,
поточна зміна оновлюється — `state = closed`, `close_date = now`,
`z_report_number = serial`; у чатер — «Shift closed. Z-Report #N». Базовий
`l10n_ua.prro.shift.action_close` лише проставляє `state/close_date` (без ДПС) —
фактичне фіскальне закриття робить провайдер. Після Z-звіту для нових продажів
потрібна **нова зміна** (Flow PRRO-6). Z-звіт при закритті зміни — обов'язкова
операція (Закон №265/95-ВР, ст. 3, п. 9). **Обмеження:** окремого XML/друкованого
Z-звіту для ДПС Odoo не формує — його зберігає та подає Checkbox; у Odoo лишається
тільки номер.

Flow PRRO-14 — Офлайн-режим і фіскальні номери. `CheckboxAPI` містить повний
набір ендпоінтів офлайн-роботи: `go_offline()` / `go_online()`
(`/cash-registers/go-offline` · `go-online`), `create_receipt_offline()`
(`POST /receipts/sell-offline`), `ask_offline_codes()`, `get_offline_codes()`,
`get_offline_time()` — для резервування діапазону офлайн фіскальних номерів і
роботи без зв'язку з ДПС. **Стан реалізації (чесно): жоден із цих методів не
задіяний з боку моделі** — немає кнопок, немає збереження офлайн-кодів у Odoo,
немає автоматичного перемикання online/offline. Офлайн-режим — фактично
**заглушка на рівні клієнта**, а не робочий сценарій. Порядок офлайн-роботи ПРРО
регулюється окремим порядком (наказ Мінфіну щодо роботи ПРРО в офлайн-режимі,
орієнтовно наказ №329 від 23.06.2020).

Flow PRRO-15 — Скасування / сторнування чека. Модель чека має стани лише
`draft → registered / error`, **без окремого стану «сторновано»/«скасовано»**.
Скасування помилкового чека фіскально виконується **чеком повернення** (Flow
PRRO-9), а не зміною стану; окремої дії `action_cancel`/сторнування в моделі
немає. У разі помилки виклику будь-якої дії запис переходить у `state = error`,
текст — у `error_message` (метод `_set_error`), і виняток піднімається користувачу.

Flow PRRO-16 — Звірка з ДПС і пошук чеків. Для звірки `CheckboxAPI` надає
`search_receipts()` (`GET /receipts/search`), `get_receipt()`,
`get_shift_info()` та `ping_tax_service()`. **Ці методи наразі не виведені в UI**
(кнопок звірки немає) — практично звірка робиться підсумками зміни в Odoo проти
кабінету Checkbox/ДПС вручну. Передавання фіскальних даних до ДПС виконує сам
сервіс Checkbox (як інтегрований ПРРО), Odoo власного каналу до ДПС не має.

Flow PRRO-17 — Друковані формати чека (text / HTML / PNG / QR). Клієнт уміє
отримати чек у форматах `get_receipt_text`, `get_receipt_html`, `get_receipt_png`,
`get_receipt_qrcode`, а на записі чека є поле `qr_code` (URL для перевірки чека в
кабінеті ДПС — вимога наказу Мінфіну №13). **Стан:** формати доступні в
`CheckboxAPI`, але **з боку моделі не задіяні** — автоматичного заповнення
`qr_code` та друку/видачі чека покупцю (паперово чи електронно) поки немає.

Flow PRRO-18 — Тайм-аути й обробка помилок API. Усі запити йдуть через
`CheckboxAPI._request` із **захардкодженим тайм-аутом 30 с** (позначено `TODO`
винести в налаштування). `requests.Timeout` → «Checkbox API timeout»,
`ConnectionError` → «Cannot connect…», HTTP 4xx/5xx розбираються в `_handle_error`
(поля `detail` / `message`). Будь-яка дія моделі при винятку викликає `_set_error`
(стан `error` + `error_message`) і перевикидає помилку — тож касир бачить причину
відмови фіскалізації.

## Звірка з законодавством

| Функція в коді | Норма законодавства | Стан відповідності |
|----------------|---------------------|--------------------|
| ПРРО як програмний РРО (`l10n_ua.prro.config`, фіскальний номер) | Закон №265/95-ВР «Про застосування РРО у сфері торгівлі, громадського харчування та послуг», ст. 2 (визначення ПРРО) | Модель відповідає; реєстрацію ПРРО в ДПС виконують поза Odoo (у кабінеті платника / Checkbox) |
| Фіскальний чек продажу з рядками, ПДВ, УКТЗЕД, формою оплати (`receipt` + `receipt.line`) | Наказ Мінфіну №13 від 21.01.2016 «Про затвердження форми і змісту розрахункових документів» (обов'язкові реквізити чека, QR/URL) | Структура полів відповідає; **рядки не переносяться з `pos.order`, `qr_code` не заповнюється автоматично** — часткова реалізація |
| Обов'язкове відкриття/закриття зміни, Z-звіт (`shift.open/close`, `z_report_number`) | Закон №265/95-ВР, ст. 3 п. 9 (Z-звіт при закритті зміни, зміна ≤ 24 год) | Відкриття/закриття через Checkbox працює; **власного XML/друкованого Z-звіту для ДПС Odoo не формує** |
| Службові внесення/видача готівки (`service_input` / `service_output`) | Порядок ведення розрахункових операцій (облік готівки в касі, інкасація) | Реалізовано (додатна/від'ємна сума на `/receipts/service`) |
| Повернення товару окремим чеком (`receipt_type = return`) | Наказ Мінфіну №13; порядок оформлення повернень | Ендпоінт `return` є, **окрема дія-кнопка не задіяна** — тип виставляється вручну |
| Офлайн-режим і резервування фіскальних номерів (`go-offline`, `sell-offline`, `offline-codes`) | Порядок роботи ПРРО в офлайн-режимі (наказ Мінфіну щодо офлайн-ПРРО, орієнтовно №329 від 23.06.2020) | **Заглушка:** методи є в клієнті, але **не задіяні з боку моделі** — робочого офлайн-сценарію немає |
| Передавання даних до ДПС / звірка (`ping-tax-service`, `search`) | Закон №265/95-ВР, ст. 3 (передавання копій до фіскального сервера) | Виконує сервіс Checkbox; **Odoo власного каналу до ДПС і звірочних дій в UI не має** |
| Відповідальність за нефіскалізацію | ПКУ, ст. 17 Закону №265/95-ВР (штрафи за непроведення операції через РРО) | Поза межами модуля (організаційний контроль) |

### Чесні застереження (FLAG)

- **Інтеграція з Checkbox — реальний HTTP-клієнт, не заглушка на рівні протоколу:**
  `CheckboxAPI` повністю покриває автентифікацію, зміни, чеки, звіти, офлайн і
  податки реальними викликами `requests`. **Проте** базовий `l10n_ua.prro.mixin`
  містить лише `NotImplementedError`-заглушки, а з боку моделі задіяно тільки
  частину методів (продаж, службові операції, X/Z-звіт, автентифікація). Повернення,
  офлайн-продаж, друковані формати, синхронізація податків у `account.tax` —
  **оголошені, але не доведені до робочих дій**.
- **Повнота офлайн-режиму — низька.** Уся офлайн-логіка (перемикання стану,
  резерв офлайн-кодів, `sell-offline`) існує лише в клієнті й **ніде не
  викликається** — це найбільша прогалина щодо вимог до безперервності
  фіскалізації.
- **КЕП касира відсутній у коді.** Модуль **не** формує й не накладає
  кваліфікований електронний підпис касира локально — підписання чеків і
  передавання до ДПС покладено на хмарний ключ Checkbox. Власного КЕП/підпису в
  Odoo немає.
- **Z-звіт / XML для ДПС неповні.** У Odoo зберігається лише `z_report_number`;
  фіскальний XML-документ Z-звіту, друкована форма та подання до ДПС виконуються
  на боці Checkbox, а не модулем.
- **Рядки чека не переносяться з `pos.order`**, `total_amount` береться прямо з
  відповіді API — фіскальний чек у Odoo лишається «шапкою» без деталізації позицій.
- **Тестів немає**, тайм-аут API захардкоджено (30 с), провайдер `vchasno`
  оголошений у Selection, але окремого модуля-інтеграції немає.
- **Наживо не перевірено:** демо-сервер не має реквізитів ПРРО/ДПС, скріншоти в
  `img/prro/` не додані; фіскальних числових прикладів у howto немає.
