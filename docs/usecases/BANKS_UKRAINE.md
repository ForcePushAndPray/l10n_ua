Тестові сценарії блоку «Банки та платежі»

Домен автоматизує роботу з банківськими виписками (імпорт операцій з ПриватБанку та monobank, розбір
транзакцій, авто-співставлення та рознесення по інвойсах), синхронізацію курсів валют (НБУ / ПриватБанк /
monobank у `res.currency.rate`) та формування платіжних посилань (QR НБУ, еквайринг monobank). Ролі:
**бухгалтер з розрахунків** (щоденний імпорт виписки, звірка транзакцій з інвойсами, курси валют) та
**головний бухгалтер** (налаштування підключень, правила співставлення, контроль проводок). Обов'язки
випливають із вимоги вести первинний облік на підставі банківської виписки як первинного документа
(Закон «Про бухгалтерський облік та фінансову звітність в Україні» № 996-XIV) та відображати валютні
операції за офіційним курсом НБУ (П(С)БО 21).

Модулі: `l10n_ua_bank_sync` (база: конфіг, завдання, виписки, транзакції, правила), `l10n_ua_bank_privat`
(ПриватБанк), `l10n_ua_bank_mono` (monobank), `l10n_ua_bank_currency_sync` (курси валют),
`l10n_ua_payment_link` (QR / еквайринг).

Flow BANK-1 — Налаштування підключення ПриватБанку (Автоклієнт). Головбух створює конфігурацію
`l10n_ua.bank.sync.config` з `provider = 'privat'`, прив'язує банківський журнал (`journal_id`, тип `bank`)
і рахунок (`bank_account_id`). Для сучасної гілки заповнюється `privat_api_token` (токен Privat24 Business →
Автоклієнт) і `privat_account_iban`; для legacy — merchant id / password / card (Merchant API). Кнопка
**Перевірити підключення** (`action_test_connection()`) валідує токен зверненням до реального API банку.
Гілка отримання виписок обирається автоматично за наявними даними (токен → Автоклієнт, інакше legacy).

Flow BANK-2 — Налаштування підключення monobank (токен, rate-limit). Конфіг `l10n_ua.bank.sync.config`
з `provider = 'mono'`, поле `mono_api_token` (передається у заголовку `X-Token`) і опційно `mono_account_id`.
Кнопка **Отримати рахунки** (`action_fetch_accounts()`) підтягує перелік рахунків із балансами через
`GET /personal/client-info`; `_mono_get_default_account()` автоматично визначає гривневий рахунок (код
валюти **980**). `action_test_connection()` валідує токен. Personal Statement API має обмеження **31 день**
на період і повертає `429` при перевищенні rate-limit — обробляється у гілці завантаження.

Flow BANK-3 — Завантаження виписки ПриватБанку (завдання синхронізації). Бухгалтер створює завдання
`l10n_ua.bank.sync.job` від конфігу, задає період (`date_from` / `date_to`). Машина станів:
`draft → fetching → fetched → processing → done` (гілка помилки → `error`). **Завантажити**
(`action_fetch` → `_fetch_from_bank()` → `_privat_fetch_autoclient()`):
`GET https://acp.privatbank.ua/api/statements/transactions` із заголовком `token` і параметрами
`startDate/endDate/acc`. Сирий payload зберігається (`payload_fetched_at`), тож повторна обробка можлива
без повторного звернення до банку.

Flow BANK-4 — Завантаження виписки monobank. Аналогічне завдання `l10n_ua.bank.sync.job` з провайдером
`mono`. **Завантажити** → `_fetch_from_bank()`:
`GET https://api.monobank.ua/personal/statement/{account}/{from}/{to}` із заголовком `X-Token`. Обробляється
`429` (rate limit), контролюється обмеження періоду в 31 день. Payload зберігається так само, як у BANK-3.

Flow BANK-5 — Розбір транзакцій виписки. **Обробити** (`action_process` → `_parse_transactions()`) розбирає
сирий payload у виписку `l10n_ua.bank.statement` (за період, із підсумками) та окремі транзакції
`l10n_ua.bank.transaction` — по одній на операцію. Для monobank суми переводяться з **копійок у гривні**,
знак задає напрям (Дт/Кт); витягуються назва / IBAN / ЄДРПОУ контрагента (`partner_name`, `partner_iban`,
`partner_edrpou`). Кожна транзакція проходить `_process_transaction()`; помилка окремого рядка логується
(`_log`), не зриваючи весь пакет.

Flow BANK-6 — Правила авто-співставлення. Головбух налаштовує `l10n_ua.bank.match.rule` (порядок за
`sequence`, перший збіг виграє). Критерії: напрям (`match_direction`), контрагент (`match_partner_id` /
`match_partner_edrpou`), текст (`match_text` у полі `match_text_field`), діапазон суми
(`match_amount_min` / `match_amount_max`). При збігу (`check_match`) правило проставляє рахунок-кореспондент
(`account_id`), контрагента (`set_partner_id`), мітку (`label`), позначає `matched_rule_id` та за
`auto_post` — автопроведення. Це дозволяє формувати проводки без ручного вибору рахунку.

Flow BANK-7 — Створення проводки з транзакції (рознесення). Для транзакції зі станом обробки натискається
**Створити проводку** (`action_create_move()`) — формується `account.move`; поле `move_id` / `move_state`
відображають зв'язок. Рахунок-кореспондент береться з правила співставлення (BANK-6), інакше — транзитний
рахунок. Захист від дублю: якщо `move_id` вже існує, `action_create_move()` кидає `ValidationError`
(«Journal entry already exists»). Додатково доступні `action_post_move()`, `action_delete_move()`,
`action_create_and_post_move()`.

Flow BANK-8 — Звірка транзакції з інвойсом (reconciliation). Прапорець `is_reconciled` та `_match_partner()`
прив'язують транзакцію до контрагента, а сформована проводка `account.move` в банківському журналі
співставляється зі знятими інвойсами штатним механізмом звірки Odoo. Правила BANK-6 автоматизують типові
надходження (за ЄДРПОУ / призначенням платежу), ручна звірка залишається для нестандартних операцій.

Flow BANK-9 — Планова синхронізація виписок (cron / auto_sync). На конфізі вмикається `auto_sync` з
періодом `sync_interval_hours` та глибиною `default_days_back`; `_cron_auto_sync()` створює й запускає
завдання за розкладом. Кнопка **Синхронізувати зараз** (`action_sync_now`) або майстер
(`action_open_sync_wizard`) виконують те саме вручну за довільний період. `last_sync_date` і
`last_sync_job_id` фіксують останній прогін.

Flow BANK-10 — Повторна обробка та відновлення після помилки. Оскільки сирий payload зберігається,
**Переобробити** (`action_reprocess`) переганяє наявні дані у транзакції без повторного fetch (зручно після
зміни правил співставлення). З `error` завдання можна повторно завантажити (`action_fetch` дозволений у
`draft`/`error`) або обробити (`action_process` — у `fetched`/`error`); `action_reset_to_draft` повертає до
початку. Текст помилки зберігається в `error_message`, події — у журналі завдання (`action_view_logs`).

Flow BANK-11 — Експорт та друк виписки. Оброблена виписка `l10n_ua.bank.statement` доступна як QWeb-звіт і
експорт у **XLSX** через контролер `/l10n_ua_bank_sync/export_statement_xlsx/<id>`. Це забезпечує паперову/
файлову форму первинного документа для архіву та звірки (Закон № 996-XIV — виписка як первинний документ).

Flow BANK-12 — Синхронізація курсів валют НБУ (офіційний курс). Модуль `l10n_ua_bank_currency_sync`, модель
`res.currency.rate.provider` з `code = 'nbu'`. **Синхронізувати** (`action_sync_rates()`) звертається до
`https://bank.gov.ua/NBUStatService/v1/statdirectory/exchange?json&date=YYYYMMDD` і записує курси у
`res.currency.rate` (по одному запису на дату, історія зберігається). Працює **без будь-яких ключів**
(публічний ендпоінт). Поле `last_sync_date` оновлюється. Це офіційний курс НБУ для бухгалтерського обліку
(П(С)БО 21).

Flow BANK-13 — Курси валют від банку (ПриватБанк / monobank). Той самий провайдер `res.currency.rate.provider`
з `code = 'privatbank'` (`https://api.privatbank.ua/p24api/pubinfo`, тип курсу `privat_rate_type`:
готівковий `5` / безготівковий `11`) або `code = 'monobank'` (`https://api.monobank.ua/bank/currency`).
Обмеження — один провайдер кожного типу на компанію (`_unique_code_company`). Курси зберігаються у
`res.currency.rate` як довідкові (комерційний курс банку, не для обов'язкової оцінки за П(С)БО 21).

Flow BANK-14 — Крос-курс для не-гривневої компанії. Синхронізуються лише активні валюти. Для компанії з
валютою обліку ≠ UAH модуль коректно перераховує крос-курс (`_uah_per_company_unit`, `_rate_vals`), щоб
курс у `res.currency.rate` завжди зберігався відносно валюти компанії, з реципрокністю гривні. Покрито
тестами `tests/test_cross_rate.py` (8 сценаріїв: реципрокність, крос-курс не-UAH, ігнорування «сирих»
котирувань, крос-курс monobank).

Flow BANK-15 — Планове оновлення курсів (cron). Крон `ir_cron_currency_sync` (`data/ir_cron_data.xml`)
викликає `model._cron_sync_rates()` із заданим інтервалом, оновлюючи курси активних валют без участі
користувача. Альтернатива — прапорець `auto_sync` на провайдері. Забезпечує щоденне підтягування офіційного
курсу НБУ на дату для валютних операцій та переоцінки.

Flow BANK-16 — Платіжне QR-посилання НБУ. Модуль `l10n_ua_payment_link`: на рахунку `account.move` поле
`nbu_payment_link` формується автоматично за шаблоном (`ir.config_parameter l10n_ua.nbu_qr_template`,
Постанова Правління НБУ №11 від 01.02.2021), кодується `base64url`, посилання —
`https://bank.gov.ua/qr/<payload>`. QR рендериться у SVG data-URI (бібліотека `qrcode`) і друкується у
формі рахунку (`report_invoice_inherit`). **Працює без ключів** — реквізити беруться з рахунку/компанії.

Flow BANK-17 — Еквайринг monobank (посилання-оплата). У банківському журналі задається `mono_acquiring_token`
(також через `res.config.settings`). На рахунку/замовленні **Створити посилання mono**
(`action_create_mono_link()`): `POST https://api.monobank.ua/api/merchant/invoice/create` із токеном журналу,
передає позиції рахунку та `webHookUrl`. Зберігаються `mono_payment_link` (pageUrl) і `mono_invoice_id`.
Потребує реального токена мерчанта monobank Acquiring.

Flow BANK-18 — Підтвердження оплати через webhook еквайрингу. Контролер
`/l10n_ua_payment_link/mono/webhook` приймає повідомлення monobank: за `invoiceId` і `status == 'success'`
знаходить замовлення/рахунок і **проводить оплату**. Це замикає цикл «посилання → оплата клієнта →
автоматичне рознесення платежу».

Flow BANK-19 — Імпорт виписки VST Bank (iBank 2 UA, файловий провайдер). Модуль `l10n_ua_bank_vst`,
`provider = 'vst'`. VST Bank (Банк Восток) не опитується по API — виписка експортується з iBank 2 UA у
CSV («Виписки по поточним рахункам», windows-1251, роздільник «;»). Майстер `l10n_ua.bank.vst.import`
(**Імпорт виписки iBank 2 UA**) приймає CSV-файл, створює `l10n_ua.bank.sync.job` (стан `fetched`,
`raw_payload = {'csv': ...}`) і запускає `action_process`. `_parse_transactions` розбирає рядки у стандартні
транзакції: Дебет → від'ємна сума (Дт), Кредит → додатна (Кт), дата операції, кореспондент (назва / IBAN /
ЄДРПОУ з колонок 8–10), призначення платежу. Далі — штатний конвеєр bank_sync (транзакції + правила
співставлення BANK-6, проводки BANK-7). Зарплатний реєстр iBank 2 UA формується майстром зарплатного
файлу (див. HR-35).

## Звірка з законодавством

- **Банківська виписка як первинний документ** — Закон «Про бухгалтерський облік та фінансову звітність в
  Україні» № 996-XIV, ст. 9. Flows BANK-3…BANK-7, BANK-11: імпорт виписки, транзакції та проводки
  `account.move` формуються на підставі виписки; QWeb-звіт і XLSX-експорт дають архівну форму документа.
- **Офіційний курс НБУ для бухобліку** — П(С)БО 21 «Вплив змін валютних курсів» + Положення про встановлення
  офіційного курсу гривні до іноземних валют (Постанова Правління НБУ, орієнтовно). Flows BANK-12, BANK-14,
  BANK-15: провайдер `nbu` тягне офіційний курс на дату у `res.currency.rate`. Курси ПриватБанку/monobank
  (BANK-13) — довідкові/комерційні, не для обов'язкової оцінки за П(С)БО 21.
- **Платіжні послуги та ідентифікація рахунків** — Закон «Про платіжні послуги» № 1591-IX; стандарт IBAN
  (Постанова НБУ №162 від 28.12.2018, орієнтовно). Flows BANK-1, BANK-2: `res.partner.bank` валідує
  український IBAN, `res.bank` зберігає код МФО.
- **QR-реквізити платежу** — Постанова Правління НБУ №11 від 01.02.2021 (стандарт платіжного QR).
  Flow BANK-16: формат посилання й шаблон реквізитів відповідають цій постанові.
- **Захист платіжних даних** — вимоги НБУ до безпеки платіжних операцій та захисту інформації (Закон
  № 1591-IX; підзаконні акти НБУ, орієнтовно). Див. застереження нижче про зберігання токенів.

### Чесні застереження щодо реалізації

- **Зберігання токенів/секретів у відкритому вигляді.** `privat_api_token`, `mono_api_token`,
  `mono_acquiring_token`, merchant-пароль зберігаються у звичайних полях моделей/журналу (без шифрування).
  Це ризик щодо вимог НБУ до захисту платіжних даних — доступ треба обмежувати правами/групами, поля
  трактувати як чутливі.
- **Відсутність КЕП / підпису платіжок.** Модулі **лише читають** виписки та формують посилання на оплату;
  вихідних платіжних доручень із кваліфікованим електронним підписом (КЕП) домен **не створює й не
  надсилає** до банку. Ініціювання платежів — поза межами реалізації.
- **Webhook monobank Personal — заглушка.** Поле `mono_webhook_url` обчислюється і є прапорець
  `mono_webhook_active`, але **контролер webhook у `l10n_ua_bank_mono` не реалізований**; real-time
  оновлення виписки не працює — синхронізація йде лише опитуванням (fetch job). Webhook **еквайрингу**
  (BANK-18, окремий контролер у `l10n_ua_payment_link`) реалізований.
- **Реальні виклики API vs демо.** ПриватБанк і monobank звертаються до **реальних API банків** — це не
  заглушки, але потребують ваших токенів; на демо-сервері ключів немає, тож завантаження виписок наживо не
  відтворюється (курси НБУ та QR НБУ — відтворюються без ключів). Legacy Merchant API ПриватБанку присутній
  як окрема реальна гілка для старих інтеграцій.
- **Покриття тестами нерівномірне.** Тести є лише в `l10n_ua_bank_currency_sync` (`test_cross_rate.py`);
  `l10n_ua_bank_sync`, `_privat`, `_mono`, `_payment_link` — **без тестів**, тож розбір payload,
  співставлення й створення проводок перевірені лише вручну.
